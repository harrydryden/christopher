# CV management audit

Scope: CV list selection, server actions, retention, generation/publication, and submitted application references. This is a review of the CV management feature and its integration points, not a whole-application penetration test.

| Vector | Finding | Resolution |
| --- | --- | --- |
| Bugs and execution | Completion was not idempotent: a repeated completion could rewrite saved metadata and archive timestamps. | Ready drafts return without mutation; an existing archive retains its timestamp. |
| Conflicts and state | All company/role operations shared one exclusive lock. Bulk actions repeatedly re-read rows, and stale editor requests could recreate a revision after parent deletion. | Per-role locks with stable ordering for bulk requests; compatibility with older workers during rolling deployment; re-check the source under the role lock before inserting an edit. Assessment retries take locks in the same order. |
| Async execution | Status polling stopped immediately after requesting a terminal refresh, so a failed refresh could leave the progress screen stuck; requests also had no timeout. Deleting a running draft prevented resurrection but did not stop subsequent model calls. | Status requests time out and polling continues until the refreshed page unmounts the component. Every stage checks whether its update found a draft; deletion exits as a skipped task. An already-running model request may finish, but subsequent stages stop. |
| Logic and fallbacks | Generation task inputs were only asserted as TypeScript types. Counts and page rows could disagree during concurrent retention. Selection used captured arrays and could survive page navigation. | Runtime task validation before model calls, consistent read snapshots, functional selection updates, shared pending state across both tables, duplicate-submit protection and selection reset on page changes. |
| Security | Bulk failures returned database exception messages, potentially including SQL and bound CV data. The legacy archive endpoint did not validate its Boolean argument at runtime. | Friendly errors, structured logs without SQL/CV contents, and runtime argument validation. Existing independent session checks remain mandatory. |
| Performance and scale | Retention loaded full CV content, evidence and assessment snapshots repeatedly; normalised role lookups scanned the table. Selection repeatedly scanned arrays. | Pure retention planners, metadata-only queries, a single group read per bulk action, indexed immutable role keys and set-based selection membership. |

The SQL queries inspected use bound parameters; CV text is rendered through React text nodes. No SQL injection, raw-HTML XSS sink or authentication bypass was found in this reviewed path. The application remains a single-user authenticated workspace; this review does not claim tenant isolation for a future multi-user deployment.

Validation covers the existing publication/archive/restore/deletion contract plus duplicate completion, archive timestamp stability, crossed bulk requests, independent role progress, collision-free indexed keys, safe database failures, stale editor submissions, request and response validation, and deletion during model analysis. All 448 non-browser tests pass; the six worker browser tests run separately. The production-build browser test exercises the editor at desktop and mobile sizes, transient status failure recovery, three archive/restore cycles, and cancelled/confirmed deletion. Type checking passes. The repository has no configured linter; its placeholder lint scripts are not counted as static analysis. Migration 0018 adds the lookup index without deleting CV data; schema generation reports no drift.

Browser verification exposed an intermittent committed-mutation/stale-screen failure. Bulk actions now use a bounded authenticated JSON endpoint and render authoritative row/count snapshots directly, without waiting for an RSC mutation transition. Both tables are read in one consistent database snapshot and share pending state and a request timeout. The endpoint validates Origin, content type, input size and selection. Response validation preserves the previous table if a malformed response arrives. Heavy CV detail links load on demand to avoid unnecessary speculative detail-page work. Related upstream reports describe [prefetch connection starvation](https://github.com/vercel/next.js/issues/96108) and [pending server-action transitions](https://github.com/vercel/next.js/issues/97990); these are supporting context, not proof that every upstream cause applies here.
