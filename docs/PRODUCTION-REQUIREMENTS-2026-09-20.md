# Production requirements review — 20 September 2026

For the executed tests, fixes, current capacity measurements, local recovery drill and read-only live observations, see [the integrated audit](PRODUCTION-AUDIT-2026-09-20.md). The matrix below separates repository requirements from production acceptance; it does not supersede those newer execution results.

## Scope and judgement

This is a read-only review of the stated jobs to be done, product requirements and production evidence in `CLAUDE.md`, `docs/SPEC.md`, `docs/UX-JOURNEYS.md`, `docs/REVIEW-PLAN.md`, `README.md`, `docs/DEPLOY.md`, `render.yaml`, `Dockerfile`, `apps/web/vercel.json` and the two GitHub Actions workflows. No tests, live-provider checks, deployment actions or production queries were run for this review.

Status means: **complete** — requirement and credible evidence are present; **partial** — substantial implementation or evidence exists but acceptance is open; **missing** — required behaviour or evidence is absent; **broken** — contradictory or known-failing production evidence; **unclear** — the authoritative requirement or deployed state cannot be determined from the repository.

The repository is not release-certified. It contains a broad implementation, strong fixture/CI intent and measured synthetic scale evidence. The 11 September production-lane benchmark exercised 1,000 companies and 100,000 jobs through the three reserved queue lanes: onboarding 29.04 seconds, unchanged scan 20.01 seconds, disruption 21.61 seconds and recovery 19.09 seconds, with no unfinished/failed tasks, 190 MiB peak process RSS and 22.60 ms p95 across 897 company-list query samples (`docs/THOUSAND-COMPANY-READINESS.md`; `docs/benchmarks/production-lanes-2026-09-11.json`). It used local PostgreSQL and synthetic HTTP, with no Chromium crawling, paid models, remote database or multi-user web load. Live-provider acceptance, the golden set, measured extraction accuracy, production recovery and provider configuration remain open (`docs/REVIEW-PLAN.md:27-34,61-65,90-98`).

## Requirement precedence

`docs/SPEC.md` v0.4 remains the normative product contract (`CLAUDE.md`; `docs/SPEC.md` introduction). Later requirements supersede older statements only where they are explicit:

- The 6 September user priorities in SPEC v0.3 put discovery/scraping, deterministic filtering, reversible table clean-up and role-specific CVs ahead of learning and recommendations (`docs/SPEC.md`, “v0.3 priorities and acceptance”; `docs/REVIEW-PLAN.md:79-98`).
- `docs/UX-JOURNEYS.md` was written on 19 September and its 20 September status records Wave 1, Wave 2 and Wave 3 implementation choices. SPEC now contains the resulting R-7.13 share-preview exception and R-7.14 Library import requirement. These supersede the older “no public sharing/import” assumptions, but retain the fixed hard-gate, shared-catalogue and verified-suggestion decisions (`docs/UX-JOURNEYS.md:3-20,322-335`; `docs/SPEC.md` R-7.13–R-7.14).
- The UX status explicitly leaves three gaps: evidence badges for education/skills, restoring an old Library version, and automatic completion of the company timeline’s scoring state (`docs/UX-JOURNEYS.md:325`). These are current requirements, not historic recommendations.
- Where the old `docs/REVIEW-PLAN.md` says a feature remained open but the dated UX status says it is built, the implementation status may be newer; the production acceptance gates in the review plan still stand until measured evidence closes them.

## Concrete production release gates

Release should remain blocked until all gates below have an owner, dated evidence and an explicit pass/fail result.

1. **Authoritative configuration:** capture the live Render, Vercel and Postgres settings; reconcile them with version-controlled configuration; confirm the now-documented three-slot Starter configuration matches production; and prove `/healthz` reports the expected commit, browser availability, AI configuration and slot count.
2. **Deployment verification:** on the release candidate, apply migrations to a production-like copy, deploy worker and web, verify both release identities, sign in, add/refresh a fixture company, complete a scan and gate, enqueue and finish a no-paid-model-safe workflow, and verify queue/Health/Operations. Add a Vercel release check rather than treating worker health as the whole release.
3. **Golden-set accuracy:** publish the roughly 25-company set required by SPEC §9, manual counts and dated results: ≥80% correct automatic discovery, zero incorrect automatic acceptance, 100% resolved with one confirmation/pasted URL, Tier-1 recall/precision ≥98%, Tier-3 recall ≥90% and precision ≥98%, recipe reproduction ≥90%.
4. **Live providers:** verify every configured Anthropic model exists, structured outputs stream as expected, current pricing feeds the estimator, Resend and Google work when enabled, and at least one real CV build is reviewed for factual grounding and document quality. Record costs and failure behaviour without exposing secrets or personal data.
5. **Correctness under failure:** demonstrate that failed, partial, timed-out, browser-stuck and OOM-recovered scans cannot close roles; lease recovery cannot duplicate completed CVs; budget reservations release correctly; a single bad company does not block a daily run; Health shows the failure within that run.
6. **Capacity evidence:** retain the 11 September 1,000-company/100,000-job synthetic production-lane benchmark as historical worker evidence. Record the new local HTTP result for 100 registered users, 100,000 `user_jobs`, 10 simultaneously active users and a separate 100-user burst. Separately agree a production-like observation or soak with the release owner that covers live provider pacing, Chromium memory and remote database connections. The only fixed duration/throughput gate here is the SPEC criterion that a 50-company daily run finishes in <15 minutes; any longer soak duration and the remaining thresholds below are proposed acceptance terms until the owner agrees them.
7. **Tenancy and security:** enumerate every page, action, API route and task payload, including intentional public/authenticated exceptions; verify unauthorised access, cross-account identifiers, shared-company mutations, share-token rate limits, cron/newsletter secrets, SSRF/redirect/DNS protections and imported hostile content. Resolve the over-broad “every page/API is 401” acceptance wording.
8. **Backup and recovery:** enable managed backups, state retention and encryption, define RPO/RTO, restore the latest backup into an isolated database, run integrity checks and an authenticated smoke journey, and record elapsed time. Document credential rotation and what happens to sessions and inbound/share links.
9. **Rollback/roll-forward:** prove the previous web and worker versions can coexist with the migrated schema for the release window, or document the mandatory roll-forward path. Exercise one failed worker release and one failed web release without losing queued tasks or user data.
10. **Operational ownership:** define who checks or receives worker-stopped, overdue-scan, growing-queue, repeated-restart, database-capacity and AI-spend signals. Add actionable alerts for release-blocking conditions or document a staffed inspection schedule with response times; the current repository explicitly has no alerting rules.
11. **Product scope:** record the three current UX gaps (education/skill evidence badges, restoring an old Library version and the scoring timeline’s completion) as optional refinements unless the release owner promotes one to a launch requirement. Learning/recommendation calibration is also a named post-release limitation. These refinements do not block release; correctness, tenancy, recovery and truthful status do.

## 100-user workload assumptions and acceptance envelope

The historical benchmark defines shared-catalogue worker scale, not multi-user activity. The confirmed launch assumption is 100 registered accounts with about 10 active simultaneously. Use the following reviewable workload for the current test and replace estimates with observed production distributions when available.

| Dimension | Assumption for test | Derived daily/burst load |
|---|---|---|
| Accounts | 100 registered; about 10 active simultaneously | Sustain 10 authenticated sessions; separately exercise a 100-user login/read burst and verify isolation for all accounts |
| Per-account role data | 100,000 total `user_jobs` across the 100 accounts | Exercise page, count, filter and write queries at realistic cardinality without cross-account leakage |
| Followed companies | At least the SPEC 50-company operational set, with shared subscriptions represented | One shared daily scan per distinct company; record the actual distinct-company and source counts rather than extrapolating from accounts |
| Sources/postings | Representative ATS, HTML and JavaScript sources; p95 2,500 roles; include at least one 40 MB listing | Exercise the required 50-company run and memory-stress cases matching the known OOM shape |
| Interactive company work | 10 active users, with a burst in which each adds or rescans one company | 10 interactive discovery/scan requests, deduplicated where a company is shared |
| Decisions and Library edits | Each of 10 active users makes 10 decisions and one Library save in the active window | 100 decisions and 10 Library saves plus their review/rescore tasks |
| CV demand | 10 builds/day; burst of 5 within five minutes; 45 KB Library and long advert at p95 | Admission, streaming, retry and budget holds exercised concurrently; cost cap set before test |
| Imports/shares | 10 imports/day, including 5 MB PDF/DOCX; 20 active share links with 10 comment writes/minute burst | Exercise extraction memory, public-token reads, write rate limits, expiry and revocation |
| Web reads | 10 steady users × 6 requests/minute, plus a separate 100-user burst; include 50-row role pages | 60 requests/minute steady plus the measured burst and polling; record database pool use and p95 response time |
| Worker | Start with the checked-in production value of 3 slots on the declared Starter plan | Do not raise concurrency until heap, RSS, Chromium and Postgres headroom are measured; pool expectation is `2 × concurrency + 4` = 10 connections |
| Database | PostgreSQL 16 basic-256mb as declared in `render.yaml` | Confirm the provider’s actual connection/memory limits; worker pool plus Vercel concurrency must remain within the explicit connection budget |

Proposed pass targets for owner agreement are: authenticated web p95 <2 seconds for ordinary reads and <4 seconds for writes that synchronously re-evaluate gates; interactive queued work starts within 60 seconds at p95; no task waits beyond its declared deadline without a visible retry/failure; no worker restart caused by memory; heap warning remains below 85% outside the deliberate stress case and recovers afterwards; no database exhaustion; no lost/duplicated terminal task; and all due daily scans finish within 24 hours. The SPEC’s 50-company batch finishing in <15 minutes is already an explicit requirement rather than a proposed threshold.

The confirmed account envelope is 100 registered users with about 10 active simultaneously; account count does not determine scan load because company scans are shared. Record and cap the actual distinct companies, sources, CV builds and imports per day. The 11 September benchmark already establishes synthetic worker and database-query headroom for 1,000 companies/100,000 jobs under its stated limits. The new HTTP result addresses multi-user web/query behaviour; a separately agreed live observation addresses provider, browser and hosted-database behaviour.

## Release decision

**No-go for production certification pending blocker evidence.** Historical synthetic worker capacity is present and is not a blocker by itself. The remaining blockers are live accuracy, an owner-agreed live provider/browser/hosted-database capacity observation, reconciled deployment configuration, web release verification, executed backup restoration against supplied RPO/RTO, rollback compatibility, live-provider validation, tenancy/security and operational alert ownership. The 100-user HTTP result should be added when complete. Education/skill evidence badges, restoring an old Library version, timeline polish, learning calibration and recommendation calibration are optional refinements and do not block an explicitly capped release.
