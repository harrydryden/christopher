# ADR 0006: LinkedIn identity, member imports and an optional private network

Status: Accepted for the initial release — LinkedIn sign-in, explicit account linking and guided own-profile uploads are implemented locally. Connections CSV and approved API imports remain future phases. No LinkedIn developer application, product approval or live-provider acceptance is claimed.

Date: 3 November 2026

## Context and decision

Course of Life already accepts a person's CV, their own LinkedIn profile PDF, pasted text or their own website through an account-owned, staged Library import. A worker extracts proposals; the person reviews individual items before they enter Experience as unconfirmed evidence. A LinkedIn URL is refused rather than fetched. [The product contract](../SPEC.md) and [ADR 0001](0001-targeted-evidence-cv.md) require anchored quotations for CV comparison and treat ambiguous or missing evidence as unknown. [ADR 0005](0005-cv-editing-modes.md) keeps a single Experience import review surface. This decision extends those contracts without turning a sign-in grant into permission to read a career, connections or jobs.

We will design three **separate, optional grants**: account authentication, the person's own profile/evidence import, and a private connections import. A UK launch can use LinkedIn OpenID Connect (OIDC) for authentication if its product access is provisioned, while preserving existing document and paste imports. An optional `Connections.csv` upload will have its own explicit consent and review. Member Data Portability API access is a later, separately approved and geographically gated path. No third-party profile browsing, LinkedIn job catalogue feed, automated messaging, posting or applying is in scope.

## Identity and account linking

The OIDC callback must validate a single-use, session-bound `state`, `nonce` and server-side authorisation-code exchange; validate the ID token signature against LinkedIn's JWKS, `RS256`, issuer, audience, expiry and non-empty subject. Use PKCE only after verifying current provider support and bind its verifier to the same transaction. A pending authentication transaction binds the provider subject to that browser session with a short expiry and one-use completion while email verification/linking finishes; a replay or different session fails. It never creates a fake email to satisfy the account schema. Tokens stay server-side, encrypted at rest where retention is needed, excluded from logs and browser payloads. The existing session row remains the application's authority.

Identity is **issuer + provider + `sub`**, never email or display name. The existing Google flow in `apps/web/lib/accounts.ts` links a verified Google email to an existing account; that behaviour must not be copied for LinkedIn. A matching email requires the person to authenticate to the existing Course of Life account and explicitly link LinkedIn with fresh reauthentication. Collision with a subject already linked to a different user fails without moving data. Missing or unverified email leaves the LinkedIn subject pending an ordinary email-verification route; it cannot satisfy the existing verified-user spending gate, administrator entitlement or migrated-owner claim. Registration-closed and `ADMIN_EMAILS` rules still apply. LinkedIn's own OIDC guidance says sign-in does not verify a person's identity. [Source](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2).

Disconnect stops future access and revokes tokens when a supported provider revocation mechanism is confirmed. Disconnecting an authentication method must not strand an account; require another usable sign-in method or a verified recovery path. Imported profile and network data have independent deletion controls. An account deletion uses the existing account-owned cascade plus explicit external-data and derived-output purge verification.

## Imports and network model

The existing `library_imports` fingerprint, byte/text caps, extraction worker, quotation anchoring and per-item acceptance remain the profile route. Its current kind `linkedin` maps to proposed source kind `linkedin_pdf`; keep the precise source, document fingerprint, import ID, exact quote and accepted-row ID. **Selecting** an import proposal inserts an unconfirmed Experience row; **confirming the fact** is a separate Experience review step. Neither changes its origin to `user_entered`, asserts that LinkedIn verified it, or proves that the online profile remains current. Comparison uses only an explicitly selected retained import and exact, unique quotations; merged, ambiguous, pruned or changed sources display **Unknown**. Ask the person to attest that a profile PDF is their own; a mismatch with their account name triggers manual review. Neither attestation nor a name match proves ownership, so source identity remains unverified.

`Connections.csv` is a separate, deterministic CSV import, not a model-written Experience proposal. Validate encoding, header aliases, row count, file size and formula-like cells before staging; deduplicate within the account by a stable public profile URL when present, otherwise leave uncertain names separate. Store only fields required for the chosen network view: name, actual archive profile URL when supplied, reported company/position and connection date. **Do not ingest email by default**; if a later purpose requires it, obtain a separate consent and review privacy terms. Display the archive's as-of date. Never infer a present-day employer, endorsement, relationship strength, referral or permission to contact from an old row. Match only a verified exact company alias automatically; an ambiguous or unmatched name waits for the owner's choice. A match to the shared catalogue produces a private, reviewable suggestion, not a shared company attribute, account follow/subscription, role score or public connection record. Contact rows are excluded from model prompts by default. No outreach, DM, invitation or application action follows automatically.

Proposed minimal contracts, to be implemented only in their phase:

| Record | Identity and required fields | Behaviour |
|---|---|---|
| `external_identities` | `userId` when linked; unique issuer/provider/subject; link status; pending session-bound transaction ID; token purpose/expiry; consent scope, time and version | Missing email remains pending without a fabricated address. Token/claim metadata stays apart from Experience; existing `auth_accounts` may be extended only with a compatible migration. |
| `external_import_sources` | `userId`, source kind (`linkedin_pdf`, `linkedin_archive`, later `linkedin_portability`), source fingerprint/version, consent purpose, status and retention dates | Owns raw upload or API provenance and deletion lineage; do not treat archive upload as API permission. |
| `import_proposals` | Source ID, original field/quote or CSV row, suggested target, selection decision, inserted Experience row ID if any, later fact-confirmation state | Selection inserts only unconfirmed Experience evidence; source attribution survives later review. Reuse the existing Library proposal flow where it fits. |
| `network_candidates` | `userId`, source row ID, minimal reported fields, optional reviewed company link, match confidence/state | Private to the account; no contact details by default and no automatic contact action. |
| `portability_sync_runs` | Consent ID, approved domain, API version, cursor, requested/completed timestamps, error and deletion lineage | Exists only after the portability gate; idempotent pagination and bounded retry. |

Purge a source by deleting its raw bytes, staged rows, network candidates and unconfirmed proposals, and resolving each derived fact whose only authority was that source under a **legal-permitted-retention decision**. A person's earlier confirmation is not an opt-out from applicable deletion duties. If retention is permitted and chosen, retain true provenance and explain what remains; never relabel the item as typed text. A durable, minimal source ledger must survive routine raw-import pruning: the current resolved-import cap of 20 cannot be the sole provenance record. Finalised PDF bytes are immutable **while retained**, but a deletion duty may require deleting or tombstoning the stored artefact, not rewriting its approved bytes. The policy for historic CV snapshots and already distributed PDFs is an unresolved launch gate. Existing account deletion is administrator-controlled, and automatic resolved-import pruning alone does not provide an owner-facing selective-source deletion path.

## Conditional Member Data Portability design

The third-party API is **disabled by default**. Its entry gate requires documented LinkedIn product approval, approved scope and permitted domains, a signed-off use of data, verified territory and a fresh member consent separate from sign-in. The [third-party product overview](https://learn.microsoft.com/en-us/linkedin/dma/member-data-portability/member-data-portability-3rd-party/) describes an EEA route, while LinkedIn's [member portability help](https://www.linkedin.com/help/linkedin/answer/a6214075) explicitly says EU/EEA **and Switzerland** members may consent to a third party. This product-specific discrepancy requires written clarification before enabling Switzerland. Neither source establishes UK access; the UK is excluded from the initial gate. Use confirmed provider eligibility rather than UI locale or a VPN.

After consent, a queued snapshot import requests only approved domains. The initial candidate list is `PROFILE`, `POSITIONS`, `EDUCATION`, `SKILLS`, `COURSES`, `CERTIFICATIONS`, `PROJECTS`, `LANGUAGES` and `VOLUNTEERING_EXPERIENCES`; each is separately mapped into proposals, not silently accepted. `CONNECTIONS`, `COMPANY_FOLLOWS`, `SAVED_JOBS`, `JOB_APPLICATIONS` and `JOB_SEEKER_PREFERENCES` need additional purpose and consent decisions. `JOB_POSTINGS` means jobs posted by the member, **not** a global vacancy feed. [Domain reference](https://learn.microsoft.com/en-us/linkedin/dma/member-data-portability/shared/snapshot-domain).

If later approved, `COMPANY_FOLLOWS` may suggest existing catalogue companies for an **explicit** follow; `SAVED_JOBS` and `JOB_APPLICATIONS` may stage personal records for review, not populate the shared jobs feed; `JOB_SEEKER_PREFERENCES` may suggest editable filters. None writes a subscription, application, gate or CV automatically. [Apply with LinkedIn](https://learn.microsoft.com/en-us/linkedin/talent/apply-with-linkedin) and [Apply Connect](https://learn.microsoft.com/en-us/linkedin/talent/apply-connect) concern employer career sites or ATS workflows, not an applicant's job-search feed. Learning, SNAP and Marketing remain low-priority, conditional investigations requiring their own permission and purpose review, as described in their linked product documentation above.

The [Snapshot API](https://learn.microsoft.com/en-us/linkedin/dma/member-data-portability/shared/member-snapshot-api) processes historical data after consent, can lag and paginates; no immediate completion promise is made. Its current documentation explicitly says to send `Linkedin-Version: 202312` and that other versions fail, despite newer documentation view dates. Treat endpoint version and permitted fields as configuration verified before each rollout, not as a guessed `2026` header. The [Changelog API](https://learn.microsoft.com/en-us/linkedin/dma/member-data-portability/shared/member-changelog-api) starts with consent and exposes only the past 28 days; absence of an event is not proof that a profile field is unchanged. A missed window requires a new permitted snapshot, not fabricated continuity.

## States and user journeys

| State | User-facing next step | No hidden transition |
|---|---|---|
| No LinkedIn link | Continue with password/Google, CV upload or paste; optionally choose LinkedIn sign-in if enabled. | Authentication does not launch imports. |
| Linked identity, no import consent | Offer own PDF/archive instructions and separate network choice. | No profile or connections API call. |
| Upload queued or extracting | Show progress and recoverable errors; duplicate fingerprint reopens the same import. | No Experience or network mutation. |
| Proposal ready | Review source quotes/CSV fields and select items. | Unknown or conflicting matches remain unconfirmed. |
| Selected from import | Save selected Experience rows as **unconfirmed**, or save private network candidates. | Fact confirmation is a later Experience step; selection does not assert LinkedIn verification or contact permission. |
| Approved portability queued | Show domain, consent, lag and sync state; allow cancel/revoke. | No fallback scraping or silent territory expansion. |
| Disconnected/revoked/deleted | Stop future sync and offer source-specific purge and account recovery. | Historical derived data is never silently relabelled. |

Recoverable errors are explicit states: OAuth cancellation returns to the unchanged sign-in choice; subject collision requires an authenticated account-linking flow; missing email holds a pending subject without account impersonation. A malformed upload retains no accepted rows and offers a corrected upload. Partial snapshot processing records completed pages and a resumable cursor, never marks missing domains empty. Permission revocation cancels queued work and fences late worker writes; rate limits honour provider retry guidance without an automatic consent renewal. Ambiguous company matches remain unlinked; deleted source data becomes unavailable rather than an apparently current match.

## Security, legal and rollout gates

Before any LinkedIn API rollout, obtain a written product/permission inventory, current terms review and a data-flow decision for **each** proposed use: identity, CV/Experience extraction, AI processing, role scoring, private network suggestions, storage, retention and deletion. [LinkedIn API Terms §§3–5](https://www.linkedin.com/legal/l/api-terms-of-use) and product-specific terms govern API content and its derivatives; member consent alone does not waive them. A user-uploaded export is a distinct ingestion path, but it is not a blanket exemption from privacy, copyright or product terms. The [Profile API](https://learn.microsoft.com/en-us/linkedin/shared/integrations/people/profile-api) expressly restricts storing other members' profile data. No scraping, LinkedIn posting, DM, invitation, automatic application or third-party profile cache is authorised by this ADR.

Roll out in gates: **0** keep and clarify guided PDF/CV/paste review for UK members; **1** provision and security-test optional OIDC, with explicit account linking; **2** add a **new** opt-in `Connections.csv` staging/parser, private matching and selective purge after privacy sign-off; **3** trial approved portability only for authorised territory, domains and purposes. The existing importer does not parse a LinkedIn archive ZIP or CSV. Each gate has an administrator-controlled flag, audit log without tokens or imported text, staged cohorts, rollback and a member-visible way to disconnect or delete. Failed approval or unavailable PDF leaves the existing CV/paste path usable.

Verification covers forged/replayed OAuth state and nonce, JWKS/key rotation, absent or unverified email, same-email/different-subject takeover refusal, closed registration and admin entitlement; foreign-account reads; duplicate and hostile CSV rows; missing email/privacy settings; stale archive company claims; anchored versus ambiguous PDF claims; consent separation; revoke/purge of raw and derived data; sync pagination, lag, cursor replay and the 28-day gap; and disabled-feature behaviour. Record conversion from upload to **reviewed** Experience, import abandonment and recovery, network match corrections, source deletion completion, OIDC link failures, and portability lag/error rates. Never use number of scraped contacts, sent messages or LinkedIn API calls as a success measure.

### Implementation map and acceptance

Use the existing auth boundary in `apps/web/lib/auth.ts` and Google route structure only as a session/callback pattern; new LinkedIn callbacks and `apps/web/lib/accounts.ts` must use subject-based linking, not Google's email-match behaviour. `packages/db/src/schema.ts` and additive migrations own consent, subject and source identity; `packages/db/src/library-imports.ts`, `apps/web/app/actions/library-import.ts`, `apps/worker/src/handlers/library-import.ts` and the Library import components own staged review. A separate account-owned CSV parser/read model prevents network rows entering Experience or shared catalogue writes. Portability gets its own worker task, cursor and revocation fence; the existing job scan remains independent. Every action and route rechecks user ownership; every queue transition is idempotent and cancel/revoke fences late results.

1. **Identity:** a valid OIDC subject signs into its linked account; cancelled, expired/replayed, mismatched-session, missing-email, same-email/different-subject and foreign-link paths cannot claim or merge another account.
2. **Profile:** a PDF/CV/paste upload reaches the existing review, selected proposals create only unconfirmed rows with anchored source provenance, and a duplicate import creates no second proposal. An unsupported archive/CSV on that form explains the separate path rather than pretending to parse it.
3. **Network:** a valid opted-in CSV yields only private candidates with archive as-of dates and actual supplied URLs. Verified exact aliases may propose catalogue matches; ambiguous/unmatched companies require an owner's decision. There is no automatic follow, score, referral or AI contact prompt.
4. **Portability:** without product approval, territory and separate consent, no API call is possible. An approved snapshot can resume a partial page safely; duplicate deliveries do not duplicate rows; rate limits retry within the provider's rules; revoked permission prevents late writes. Missing domains and changelog gaps stay unknown.
5. **Deletion:** a source-specific purge removes staged and network data, resolves derived evidence under the legal retention decision, and records any retained historical artefact honestly. Deletion or tombstoning of stored final PDFs is supported when required; no rewritten bytes masquerade as the approved original.

## Proposed screens and product opportunities

The initial onboarding route is **Continue with LinkedIn → Add your experience → Review → Ready to build**. Reuse the existing Experience review rather than introduce a separate LinkedIn wizard. Signing in prefills only returned identity fields; do not describe it as importing a career.

Confirmed changes follow the existing CV source-change flow, preserving refinements and saved manual versions. |

Import extraction uses the existing bounded processing and cost controls; retrying authentication must not enqueue extraction or consume a CV credit. ## Administrator setup and delivery sequence

1. Create the LinkedIn developer application, associate and verify the organisation's Company Page as required, and request the OIDC product. Register exact production and test callback URLs and configure server-side credentials without exposing them to the browser.
2. Document the permitted production scopes, consent wording, privacy policy, retention rules and support contact. Verify actual returned claims with test accounts, including missing email. Do not make production availability contingent on development-only access.
3. Implement and test the identity adapter, explicit account linking and guided existing uploads first. Roll out behind a flag; measure sign-in completion and time to the first reviewed Experience item against existing onboarding.
4. Implement the optional connections CSV parser, private matches and deletion controls as a separate release. Test with representative consented exports and stale/ambiguous company records before enabling it.
5. Apply separately for third-party portability if eligible-user demand justifies it. Confirm country coverage, approved purposes and fields with LinkedIn; obtain real approved fixtures before implementing field mappings. Trial career import first, with network/history domains remaining separate opt-ins.
6. Evaluate `/identityMe` Plus only if its approved commercial terms and limited prefill materially improve onboarding. Do not put partner approval, price or delivery dates into a customer promise before confirmation.

These are proposed implementation tasks. This ADR does not claim that an application has been registered, permissions granted, live endpoints tested or any integration deployed.

## Open decisions before implementation

1. Confirm OIDC product provisioning, permitted claims, issuer/JWKS behaviour, PKCE support and exact account-linking terms for this app. No developer key or existing Google integration proves this.
2. Obtain a product-specific LinkedIn answer for portability territory, especially Switzerland; UK is excluded from the initial gate. Confirm approved domains, API agreement, AI/score/storage permissions and deletion duties.
3. Approve a retention schedule and selective purge design for uploaded exports, accepted evidence, network matches, CV snapshots and finalised documents. The service's immutable-PDF rule governs the bytes while stored; it cannot override deletion duties. Decide when to delete or tombstone stored artefacts and how to explain copies already distributed.
4. Decide whether optional network information is useful enough to justify handling other people's data. Keep the CSV phase disabled until that decision and a privacy review are complete.


## Initial-release implementation record — 3 November 2026

The initial release extends the existing account system rather than replacing it. Migration `0071_linkedin_oidc.sql` adds browser-bound pending authorisation records and records the authentication method on sessions. `jose` verifies signed LinkedIn identity tokens against pinned issuer, audience and public keys; callbacks consume state once. No provider access token is retained. New identities are shown their email and a choice to create an account or use an existing one before any account is created. Known subjects return to their original account without replacing its email.

Matching emails pin linking to the existing account. An unseen or missing LinkedIn email may also link to an existing verified account after fresh password or Google proof. New users whose provider email is unavailable or unverified complete a browser-bound application email check. An existing account's identity, Experience, CVs and credits remain unchanged by linking. A single normalised email cannot create duplicate accounts, including concurrent requests; unrelated email addresses cannot establish human identity, so the explicit account choice remains essential. Administrator/bootstrap addresses use the established registration/recovery flow rather than acquiring privileged ownership from a new LinkedIn registration.

New accounts without an explicit destination open `/library?onboarding=linkedin`, expanding the existing own-PDF instructions. Users may instead upload a CV or paste text. The upload action requires an own-profile declaration for LinkedIn PDFs; declaration is not independent identity verification. Existing proposal review and evidence confirmation are preserved.

Disconnect requires recent authentication through a usable alternative method and removes local LinkedIn associations and LinkedIn-created sessions. It does not revoke the grant on LinkedIn's side or remove uploaded documents, Experience or saved CVs. Members can revoke the application separately in LinkedIn. Completed transactions clear personal claims; bounded maintenance removes expired pending records.

Verification uses genuinely signed JWT fixtures, database-backed identity and concurrency tests, server-action and route access checks, password/Google compatibility tests, import and maintenance regressions, and a browser journey with a synthetic provider identity. The browser journey linked a different LinkedIn email to the existing password account, preserving its primary email and three credits; the database contained one account for that user and no account for the differing LinkedIn email. These checks are not a real LinkedIn authorisation round trip.

See [LinkedIn sign-in setup](../LINKEDIN-SIGN-IN.md) for provisioning, migration and required hosted acceptance checks. The initial release does not implement the broader source-deletion or network-import contracts described for later phases.
