# ADR 0007: A lifelong career record, flexible CV presentation and private recommendations

Status: Implemented and locally verified for C1–C6; hosted CI and review pending. 11 November 2026.

This decision supersedes the confirmation and CV-shaped storage policies in ADR 0001 and the global Experience capture parts of ADR 0005. It retains account isolation, immutable saved CV inputs/final PDFs, explicit paid generation, independent Manual editions and role-scoped Refine wording. It does not launch employer advertising, recruitment access or a new payment product.

## 1. Outcomes and boundaries

Experience is a lasting, editable career record. Preparing an application should enrich that record without repeated approval steps, while several truthful perspectives can coexist. Employment, contracting, consultancy, fractional work, client delivery, projects, volunteering, learning and qualifications must not be forced into one linear employer/title history.

A person can start with a short narrative, add detail during a CV question, navigate from the resulting claim to its source, correct it and reuse it for another role. Their own factual input is usable by default. Coaching is optional; neither a completeness score nor an unresolved qualitative conflict prevents technical-safe CV completion.

The same private record supports useful company and vacancy recommendations without first following companies. Explicit preferences constrain matching. Shared catalogue records remain public/source-derived; personal evidence and scores remain account-owned. Future promotion is a separate placement concern, never a reason to alter organic fit.

All changes below are part of this build unless explicitly marked future promotion or external validation. Stages describe delivery order, not permission to stop at a schema or specification.

## 2. Domain model

| Entity | Responsibility | Identity and history |
| --- | --- | --- |
| Career record | An organisation reference, engagement, role, project, contribution, skill category or learning/qualification/other activity; structured labels/dates plus original narrative | Owned stable UUID, revision, active/archive state; no identity inferred solely from names/dates |
| Career link | Employer, contracting intermediary, client/delivery organisation, membership or contribution relationship | Owned stable UUID and typed endpoints; parallel and many-to-many links permitted |
| Assertion | Exact user-supplied statement about a record, optional facets and bounded structured context | Owned stable UUID and append-only versions; not keyed by text or display position |
| Perspective | A reusable emphasis or interpretation referencing assertions, such as leadership or operational delivery | Stable identity and dependencies; does not invent a second historical event or factual corroboration |
| Provenance | Original narrative/input, source kind/reference/quote, capture context and actor | Retained when text is accepted, edited, superseded or organised; acceptance never rewrites origin |
| Change | One user intent affecting one or more records/links/assertions | Idempotency key, expected affected revisions, before/after references and undo relationship |
| CV projection | A selected, immutable input view with source identity mapping | Records career version, presentation choice and assertion-version references; historical citations retain their original interpretation |

The storage implementation may use typed version payloads rather than one SQL table per conceptual noun, but record, assertion and change identities are first-class. It must not encode a project or client merely inside a heading string. A relational database with JSON payloads and indexed ownership/identity is sufficient; no graph database is required.

Each record retains an original narrative even when optional organisation extracts structured fields. A nonblank user narrative is itself usable evidence with a stable record-narrative identity and revision; the person never has to retype it as separate assertions before a CV can use it. Approximate/unknown dates remain approximate/unknown. Two simultaneous current engagements are valid. Projects can span roles and involve several organisations. A contribution can reference more than one project without being duplicated as independent evidence.

An engagement distinguishes employment, contract, consultancy, fractional, self-employed and other arrangements. The organisation that employs or contracts the person is not automatically the delivery client. Confidentiality stores the private relationship separately from an explicit public label, such as “Confidential healthcare client”. A public label supplied by the user is not independently verified. CV generation, display metadata and public exports use the permitted label; private names must not leak through heading reconstruction, recommendation explanations or generated context. Ordinary role or date edits never overwrite the private organisation identity accidentally. Confidential sources are excluded by default. To reuse a contribution safely, an assertion may carry explicit user-entered `publicText` alongside its private original and the record/link public label. Only that public wording and permitted display metadata enter CV author/reviewer context; no automatic name-redaction guess is made. The editor shows “CV wording” only where needed. Recommendation profiles conservatively exclude these confidential sources even when a public CV version exists.

## 3. Trust, capture and compatible perspectives

| Input | Save behaviour | Reusable factual status |
| --- | --- | --- |
| User types a fact in Experience or answers a clearly labelled factual question | Save the original answer immediately once, with a visible destination and undo | Usable user assertion; not “verified” |
| User accepts source-backed document rows | One acceptance saves selected rows and provenance | Usable; no second Confirm step |
| Existing saved Library rows | Migrate conservatively with legacy provenance | Usable unless known to be unaccepted/model-only proposals; historic confirmation metadata remains history |
| Model organisation/paraphrase | Save separately as derived organisation or perspective, preserving supporting assertion references | Never independent evidence; unsupported additions remain suggestions |
| Ordinary Refine wording, including bullet title/body | Save the role refinement and CV edition | Application wording, not global facts |
| Manual edit | Save the independent edition | Final-document-only; no extraction, preference learning or factual promotion |

The capture interaction supplies intent. A factual question visibly says which Experience item receives the answer; submitting it does not require an additional “I confirm” checkbox. A CV wording editor does not silently acquire a global-fact side effect. “Add a factual detail” opens a contextual Experience editor and saves directly there. A deliberate later promotion of selected Manual text remains explicit because it changes scope, but has no redundant confirmation after that choice.

Durable saving is deterministic and free. It does not wait for an LLM, enqueue paid CV generation or replace the selected CV. Background organisation can fail/retry independently without losing the original answer. Unsupported model output is never converted into user-authored evidence by normalisation or acceptance of unrelated rows. No absence of a conflict is described as proof of truth.

Different perspectives are compatible when they describe different aspects of the same activity. “Managed six direct reports” and “coordinated a twenty-person programme” are not automatically contradictory. A real conflict concerns the same subject, attribute/metric, scope and overlapping period with incompatible values. Narrative similarity alone must not merge records or label a conflict. Uncertain matches remain suggestions.

Conflicts are local and advisory. Save both inputs; show the precise affected item and choices to keep both with context, correct, supersede or dismiss the suggestion. Do not block unrelated saves, CV generation or explicit finalisation. The writer must not silently combine incompatible numbers into a new claim. When unresolved, preserve an explicitly selected version or omit the disputed detail and report the gap; never arbitrarily present the newest model guess as settled truth. Conflict detection is deterministic for explicitly structured subject/attribute/scope/period values; it does not pretend to detect arbitrary contradictions in prose. The immutable projection reports omitted assertion IDs, while the existing Experience conflict notice offers local review and correction. Recommendations use only explicit role, skill and industry terms; perspective labels do not introduce private narrative into catalogue matching.

## 4. Write, read and recovery contracts

The concrete service surface is account-scoped and authenticated:

- `getCareerWorkspace({recordId?, cursor?, assertionsCursor?, linksCursor?, changesCursor?})` is the authenticated action over an account-scoped reader. It returns summary metadata, the selected record and paginated related assertions/history. It must not serialise the complete lifetime record repeatedly into every editor. Record pagination uses a timestamp-and-ID cursor so records saved at the same time remain reachable.
- `saveCareerChange({expectedRevision, operations, requestKey})` accepts a bounded discriminated operation set: create/edit/archive record, link/unlink relationship, add/edit/retract assertion, or save/remove perspective. Ownership comes from the session, never a trusted posted user ID. It returns the committed revision, stable changed IDs, saved values and advisory conflicts.
- `undoCareerChange({changeId, expectedRevision, requestKey})` appends a compensating change. It refuses to overwrite newer edits to the same affected object without an explicit resolution; unrelated changes do not disappear.
- Import acceptance and quiz/capture actions call the same write service with source provenance and an idempotency identity. Retrying a response cannot duplicate facts, queue a second continuation or charge again.
- `careerCvEvidence(userId, careerVersion, selection, presentation)` returns a deterministic immutable CV-compatible snapshot and assertion-version/source-ID mapping. It never mutates the source record to satisfy a CV row or page limit.
- `careerRecommendationProfile(userId)` returns a deterministic account-private profile and version/hash from eligible explicit skill assertions, roles and industries. Manual/application text and model-only proposals are excluded. It carries no sponsor or bid fields.

An account head version orders snapshots; affected entity revisions prevent stale overwrites. The first implementation may serialise writes per account, but must recover unrelated edits rather than force a reload that discards text. Request keys bind the complete intent. Unknown IDs, foreign ownership, invalid relations, unsupported field types and oversized operations are technical errors; opinions about writing quality are not.

Autosave commits small completed edits (blur/add/remove/move or an explicit answer submission), not every keystroke. A single-flight queue coalesces the same field's pending changes and keeps later text visible. The interface shows Saving, Saved or Retry and never says saved before acknowledgement. Failed writes retain the buffer. Refreshes and background results cannot replace dirty text. Undo operates on the actual acknowledged change, not a guessed local index.

The common existing Library writer is an integration boundary: document import, gap quiz, evidence conversation, accepted skills and legacy editing cannot continue writing an independent source of truth behind the new record. After adoption they route through the career writer or a compatibility adapter within the same account lock/transaction. The compatibility snapshot is published with its exact career version. No recursive dual-write loop or eventual-consistency window may produce a current CV from half a change. After adoption, the older supporting editor is restricted to About/contact, appearance and writing preferences. All factual entries, including qualifications, learning and skill categories, have one editable home in the career record. The server refuses legacy factual mutations while accepting unchanged factual payloads on profile-only saves; imports and explicit factual capture use the trusted compatibility writer. This prevents an old edited statement and its replacement both being published as current facts.

## 5. CV use and presentation

Career storage has no per-job twenty-row limit. Defensive request/page bounds remain, with pagination and search for larger records. CV limits apply when selecting evidence for an output, and any omitted material remains navigable in Experience. Selection follows explicit role priorities, treatments, source eligibility and page/font capacity; it does not silently discard later-career records because they were beyond a database page. The compatibility projection ranks the full eligible candidate set against the role and explicit priorities before its bounded input envelope. A matching saved perspective can boost its linked eligible facts for retrieval, but its label or note never becomes evidence. The projection returns capacity/conflict exclusions and preserves source identities; it is not a promise that every saved fact appears in a CV.

Chronological, project-led and hybrid presentation are explicit choices in shared Layout. Chronological groups selected contributions beneath roles/engagements. Project-led groups selected contributions beneath projects with their public client/organisation and date context. Hybrid includes role history plus project highlights without counting the same contribution as independent corroboration. Unsupported/missing project structure falls back transparently to an available grouping rather than inventing a project or employer. Storage order and source identities do not change when presentation changes.

The mapping must preserve assertion IDs across reordering, edits, projection and compatible source updates. Legacy `entry:<id>:row:<index>` references remain scoped to the original saved Library snapshot; they must not be rebound by position to new facts. New snapshots retain an explicit map to stable assertion versions. For every edition, `librarySnapshot.careerProjection` is the authoritative source pin used by source navigation and rebase. Nullable top-level career fields record generation provenance and Auto publication; a Manual or Refine edition is not reinterpreted merely because those optional columns are null. Generation continuations copy their exact saved projection metadata, including a quiz continuation, without rereading newer facts. Exact Refine locks remain attached to their stable targets and retain original source dependencies; incompatible changes remain visible conflicts. Current/saved Manual content and approved PDFs stay unchanged until the user deliberately creates another edition.

A displayed claim has an “Edit Experience” link to the underlying source record/assertion. Where several sources support it, show those choices rather than opening an arbitrary first source. Edits return to the same CV context with a clear source-update opportunity. A factual answer can enrich Experience while the original build continues once against its recorded updated snapshot; it does not start a new paid build implicitly.

## 6. Experience interface

Experience provides an overview/search with roles and engagements, projects, learning/qualifications and other activities. Opening a record shows the original story, linked contributions/assertions and relevant relationships. Reuse compact existing design-system forms and disclosures; do not introduce one large confirmation card per sentence.

The primary action is editing or adding the next useful detail. Confirmation checkboxes, Confirm all and quality-gated readiness are removed from user-authored/accepted facts. Optional coaching and organisation are secondary. Source and privacy information remain inspectable without repeating warnings above every input. Multiple perspectives are presented as views of one underlying experience, with clear links to their sources.

CV factual questions use the same editor/capture contract. A saved answer reports its actual destination and offers Undo/Edit. Confidential public labels, employer/client distinction and parallel dates are first-class controls. Empty, loading, saving, failure/retry, archived/history and soft-conflict states all preserve navigation and recoverability. Keyboard operation and 390px layouts remain usable.

Skill labels use a reusable, accessible multi-select tag control rather than requiring a combined prose list. Existing labels can be selected together, removed individually and explicitly added where the editing scope permits. The persisted representation remains ordered `skillItems`; selection does not alphabetise existing choices, split legitimate comma-containing labels or remove the existing reorder controls. A new Experience tag is a user-entered career fact; a Manual tag belongs only to that edition. Refine selects supported source skills or applies an explicit remembered wording edit and never silently turns an application label into global evidence. This does not introduce a mandatory taxonomy, infer proficiency or change generated-skill grounding rules.

## 7. Private company and vacancy recommendations

The shared catalogue remains one copy of each verified company, career source and observed vacancy. Personal profile content, match features, explanations, dismissals and application decisions always carry account ownership. No personal evidence is written into shared company profiles or exposed to employers.

A zero-follow user can receive recommendations from eligible shared catalogue companies and actual currently open observed vacancies. Following is a deliberate subscription/monitoring choice, not a prerequisite to seeing a suitable opportunity. Recommendations do not silently follow companies, create applications, send messages or apply. A company with no observed matching vacancy is clearly a company recommendation, never a fabricated role.

Explicit location/keyword/other preference constraints retain priority over inferred relevance. Negative decisions remain respected. Unknown location or insufficient vacancy evidence is labelled rather than guessed. Initial ranking is transparent lexical relevance, not a validated guarantee of suitability or fit quality. A bounded deterministic ranking provides an explainable initial result without a model call for each view/save; any optional model assistance uses existing verified-user, budgeting and caching contracts. The profile version, preference version, catalogue/job freshness and ranking contract form the result identity; advertising is never part of this fingerprint. The initial reader is `getCareerRecommendationProfile(db, userId): Promise<{version, hash, roles, skills, industries, terms} | null>`, derived from the full eligible career record rather than the bounded CV selection. Only permitted skills, role titles and industry/capability terms enter matching and explanations; no raw narrative, contact details or private client names are sent to an external model.

Organic explanations describe the relevant capability, role or stated preference, not sensitive personal details or confidential client identity. Show actual vacancy source/link and last-observed information. Public recommendation candidates must be shared, have no private/manual owner, be open and have been observed within the preceding 30 days. Last-observed freshness is not a guarantee that a vacancy remains open. Closed postings are excluded using the existing scan-completeness/closure rules; this work must not weaken the two-successful-miss policy. Paginate candidate retrieval and use bounded indexed queries; do not join every assertion to every job on a page request.

The user can correct their Experience or preferences directly from a recommendation and understand the difference. A change invalidates dependent private ranking inputs without overwriting historical CV inputs or turning a career fact into a job-search preference. Sparse/empty Experience uses explicit preferences and honest catalogue discovery; it does not demand follows or make up a career profile.

## 8. Future employer promotion: extension boundary, not launch

Future campaigns would have a separate verified advertiser/organisation ownership model and explicit placement identity referencing an existing eligible company/vacancy. Organic match scores and explanations cannot include payment, bid or campaign status. A separate placement composer may later select clearly labelled advertising from independently eligible candidates; preference constraints and closed-vacancy exclusions still apply.

No campaigns, bidding, billing, advertiser access, targeting UI or sponsored feed are enabled in this build. Preserve a clean organic recommendation provenance contract now. A future launch requires programme/product/legal review, advertiser verification, reporting/removal controls, clear adjacent advertising labels and a separate privacy assessment. Private CV/evidence or sensitive inferences are not employer targeting data.

Official ASA guidance says paid recommendations/native advertising must be obviously identifiable as advertising; ambiguous labels such as “Sponsored” alone can be insufficient. Use an explicit nearby “Ad”/“Advertisement” design if a future placement is approved: https://www.asa.org.uk/advice-online/recognising-ads-native-advertising.html . ICO guidance requires additional conditions and safeguards for special-category processing; endpoint capability or a generic consent checkbox does not establish permission: https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/lawful-basis/special-category-data/what-are-the-rules-on-special-category-data/ . These references constrain future design, not a claim that this implementation has received legal approval.

## 9. Migration and compatibility

Use additive unpublished migrations, with fresh-chain and populated-upgrade tests. Assign deterministic migration identities to existing saved Library records/rows and retain the original JSON/version. Existing stored rows receive honest legacy provenance; old confirmation flags remain historical metadata, not a new factual gate. Unaccepted import/model proposals remain proposals. Migration does not turn accepted uploaded text into independently user-entered or externally verified content.

Do not merge similar companies/roles/projects automatically or infer confidential relationships. Existing simple employment becomes the simplest engagement/role structure; additional relationships can be edited later. Preserve unknown dates and parallel work. Historical CV content, source snapshots, application references, final PDFs and public shares remain byte/identity compatible. A model-only suggestion cannot become usable merely by passing through the compatibility writer.

Publish the new reader/writer and compatibility adapter together behind a versioned schema contract. Background jobs pin the appropriate source version; retries remain compatible during rollout. Worker deployment precedes web paths that enqueue new payload shapes. No production migration/deployment is authorised by completing this local build. Rollback disables new entry points while retaining additive records/history; it must not discard saved user data or revert to a stale pre-migration Library.

## 11. Coherence decisions and verification record

- Saving a fact and generating a CV are separate transactions/intent boundaries. No background organisation controls whether the original input exists.
- A perspective references assertions; it is neither another employer nor independent proof. Application wording is still a different scope.
- User trust and model trust are different: no accuracy-policing gate for the person's statements, no invented model evidence.
- Record revisions and immutable CV snapshots solve different problems. Changing current Experience never edits a final document.
- Presentation can regroup the same career history without changing identity, chronology or confidentiality rules.
- Recommendations use a private projection of career evidence; shared catalogue ownership, explicit filters and vacancy truth remain authoritative.
- Promotion is an explicitly deferred product. Only the boundary/provenance design is delivered now, never hidden organic-score influence.
