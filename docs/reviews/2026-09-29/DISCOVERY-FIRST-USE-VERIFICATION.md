## Defects and resulting behaviour

Discovery previously let repeated references lift a named wrong-company board above automatic acceptance. It also stopped searching as soon as a sufficiently ranked board verified, before applying the identity checks used in the final result. Named identity contradictions now remain below automatic acceptance, early stopping uses effective confidence, and corroboration counts distinct methods rather than repeated evidence strings.

An “All jobs” label could promote a URL carrying an office/category filter. Discovery now treats scoped or unknown query parameters conservatively, while allowing recognised tracking, locale and initial pagination parameters. A narrow shared detector also checks selected controls in job-filter regions. It ignores unchecked options and unrelated sorting/language controls. Filtered zero results cannot establish an intentionally empty full board. This is a targeted heuristic, not a claim to recognise every possible site-specific filter.

The crawl can follow a second explicit full-listing link within fixed hop and existing total budgets, covering portal chains without increasing general crawl depth. One explicitly linked rich listing with a loading state or a recognisable empty job-search results mount can use the guarded browser. Promotion requires distinct posting identities; a loading screen alone stays unresolved. Rendered candidates retain body/identity hashes and use the final rendered URL for scope checks. HTTP refusal and robots denial are not treated as reasons to bypass restrictions.

First-use browser work exposed a separate preferences defect: saving only locations created a gate containing default “operations” keywords and marked the setup step complete. The initial Settings experience now uses the combined keywords-and-locations form, with server-side enforcement. Review also found that independent manual saves built a whole gate before acquiring the account lock, allowing a concurrent save to be overwritten. Submitted fields now merge under the lock against current settings. The corrected initial form was exercised in a real browser, including focused validation errors; the complete cold journey is documented in [First-use live verification](FIRST-USE-LIVE-VERIFICATION.md).

A real scan with AI disabled also labelled unscored roles “budget spent”. A distinct unavailable state now separates missing AI from an exhausted budget. A subsequent cold run found that scans skipped creating score tasks and left the state null; scan fan-out now records the skip reason directly for eligible, never-scored views. The update is restricted to that scan’s candidate pairs and protects newer scores, queued work and decisions. Historical ambiguous rows are not silently reclassified. An independent review retains a narrower follow-up: preference re-evaluation and description enrichment still enqueue scoring before runtime model availability is checked. Their no-key rows can briefly show scoring until the worker records unavailable, especially with batch scheduling. The scan correction does not claim to fix every scoring producer; a shared admission-context design and no-key/batch recovery check remain necessary.

## Comparable live budgets

Earlier live diagnostics used 16 fetches and 45 seconds per company, although production discovery defaults are 40 fetches and 120 seconds. The harness now names these modes explicitly and retains the old diagnostic mode for historical comparison. Each result records limits and source-selection provenance. Serial execution avoids consuming crawl time while waiting behind another case's shared browser lane; it does not by itself make the whole test production-equivalent.

## Whole-corpus failure, independent label review and targeted repair

The first new 25-company run at production crawl limits returned **17/25 correct automatic selections (68%)**, 19 source matches including confirmation candidates, and two automatic selections that disagreed with its frozen labels. It therefore failed. The two disagreements were Cloudflare’s Greenhouse feed and Zapier’s Ashby feed, observed in network requests from their first-party listings. The [original JSON](implementation-evidence/discovery-production-budget-25.json) and [per-case report](implementation-evidence/DISCOVERY-PRODUCTION-BUDGET-25.md) are preserved; neither is rewritten after the label review.

A separate reviewer then inspected the official listings with a browser and enumerated raw vendor JSON independently of the product parser. Cloudflare’s fully expanded page displayed 402 roles and matched all 402 feed URLs/IDs, with no difference in either direction. Zapier’s 10 visible roles matched all 10 listed feed jobs. The browser responses and separate GETs also had identical raw hashes. Astra accepted these as point-in-time source aliases. The manifest now names **only these two typed alternatives**, retaining the original HTML labels; matcher tests reject other types, boards, detail pages and scoped URLs. This corrects source identity evidence, not posting quality or all-channel coverage. [Independent equivalence audit](SOURCE-EQUIVALENCE-AUDIT.md).

Datadog still made no render attempt in that whole run. A guarded static read found empty `#searchbox`, `#hits` and `#pagination` mounts inside `#job-openings`, despite substantial navigation and no loading text. A generic mount detector now recognises that structure only on an explicit unfiltered full-listing hop, under the existing single rich-page render allowance. Held-out checks cover successful hydration, still-empty results and unrelated product search. The [bounded Datadog recheck](implementation-evidence/discovery-datadog-mount-followup.json) resolved the exact labelled page at 0.85 with one render, five fetches and ten initial posting identities in 12.8 seconds. Those ten identities establish the source; they do not claim the full 414-job extraction observed in the earlier continuation checkpoint.

The [final serial 25-company rerun](implementation-evidence/DISCOVERY-PRODUCTION-BUDGET-FINAL-25.md) ran from 15:59:41 to 16:09:29 UTC using production budgets, the repaired discovery code and explicitly adjudicated labels. It returned **20/25 correct automatic sources (80%), with zero wrong automatic accepts**. Twenty-one sources matched when confirmation candidates are included. This passes the numerical source-selection threshold. The harness correctly retains a blocked overall verdict: no extraction ran and independently labelled posting recall/precision remain unmeasured. OpenAI, Salesforce, Spotify and Revolut remain mismatched/unresolved; Netflix matches only with confirmation. No score is raised merely because one component gate passes.

## First-use outcome and empty-result recovery

The final fresh confirmed account saved its deliberate preferences, followed Render through the interface, resolved its Ashby board automatically and received 40 postings, with 17 matching roles. All 17 show “AI scoring unavailable; review manually”, with zero model calls or futile scoring tasks. The account and database were initially empty apart from the synthetic confirmed identity; email verification was not exercised. This is a real public-source observation through the local web/queue/worker/database flow, not an unaided usability session.

Changing the same account's keyword to Paleontology, without another scan, exposed an empty-table navigation defect: archived former matches caused the page to open an empty Shortlisted tab. The default now remains Matched when both live tabs are empty, preserving explicit tab choices and the populated-shortlist fallback. The empty Matched explanation reads account monitoring facts, distinguishes unfinished/failed monitoring from a successful scan, and links to the appropriate next action. Independent review subsequently challenged company-filtered empty results: the account-wide success cannot describe an unscanned selected company. That case receives neutral company-specific guidance instead. Restoring Engineer returned all 17 roles from the same stored 40 postings. Health now explicitly labels its daily-run history so users do not confuse it with individual company scans. The [first-use evidence](FIRST-USE-LIVE-VERIFICATION.md) records each intermediate failure, runtime identity and final browser result.

Scoring can also finish after the scan task disappears. Previously Roles stopped polling at that boundary and could retain a stale scoring label. Its work query now includes only this account's live scoring/rescore tasks and provider-batch membership, while Companies continues to track company work alone. Future batch work remains observable using the existing unchanged-result backoff from ten seconds to one minute and hidden-tab suspension. Focused database tests verify the late-score transition, account isolation and future batch hand-off; no real provider output is claimed.
