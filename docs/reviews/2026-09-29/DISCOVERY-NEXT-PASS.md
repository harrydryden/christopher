A later [bounded Mozilla recheck](implementation-evidence/source-wise-mozilla-final.json) repaired the wrong automatic selection. **16/25 is an inference across separate observations, not a measured whole-corpus score.** The final candidate must be rerun against all 25 labels before claiming progress towards the ≥80% (20/25) automatic source gate with zero wrong accepts. ## Priority 0: prevent filtered listings from gaining automatic confidence

`isExplicitCompleteListingLink` accepts a strong link label before checking whether the target has a filtering query (`packages/core/src/discovery/discover.ts:348–358`). A link reading “All jobs” can therefore carry `?office=london`, `?bc=DB` or another scope restriction. Tighten this precondition before promoting any further destinations: distinguish known pagination/tracking/locale parameters from actual scope filters, and keep unknown filter-like keys at confirmation. Retain parameters needed to fetch the page, but distinguish them from evidence that its scope is complete. The current test for filtered `/positions?office=london` (`packages/core/src/discovery/discover.test.ts:364`) is a useful starting fixture; add an explicit “All jobs” label pointing at that filtered URL, plus Salesforce-shaped `?bc=DB`, a paginated unfiltered listing and a tracking-only link. A filtered APAC page must never outrank a verified company-wide listing or become an automatic accept.

## Priority 1: follow a second explicit complete-listing hop

Every discovery `visit` starts with depth one (`packages/core/src/discovery/discover.ts:751`), and a landing page spends that depth when following its first onward link (`:512–532`). Siemens' first-party chain is **company Jobs → externaljobs portal → SearchJobs**; the current result stops at the portal/landing page at confidence 0.5, while [independent navigation evidence](SOURCE-LABEL-AUDIT.md) shows job-detail links on SearchJobs. Permit one further hop only along an explicit, first-party complete-listing anchor. Bound it by normalised visited-URL identity, a fixed branch/chain limit and the existing total fetch/render and discovery deadlines (`packages/core/src/discovery/discover.ts:15–27, 79–93`); do not increase general crawl depth for culture, location and team pages. Require actual distinct posting links or valid `JobPosting` data at the destination before using the existing `listing_html` confidence of 0.85 (`packages/core/src/discovery/confidence.ts:19`).

Held-out checks: Siemens-shaped two-hop portal reaches SearchJobs; a careers article containing several editorial cards and a separate All Jobs link selects the latter; a portal loop terminates; a filtered All Jobs link remains confirmation; an unrelated-domain redirect cannot inherit first-party confidence. The [Mozilla editorial-card fixture](../../../packages/core/src/discovery/discover.test.ts) should remain automatic for its genuine listings destination and never regress to the careers root.

## Priority 2: verify dynamic first-party listing pages once, late in the crawl

The renderer currently runs on a candidate only when the page is a sparse JavaScript shell or contains an *empty* job mount (`packages/core/src/discovery/discover.ts:326–334, 459–476`). A content-rich page with “Loading roles”, “fetching statistics” or an unhydrated job-board component can be the explicitly linked all-jobs page and still retain only `landing` confidence 0.5. This matches the bounded observations for Datadog, Cloudflare and Zapier, whose **correct source URLs** were confirmation-only. Spotify's first-party `/jobs` has a similar loading/filtered-zero shape, but a guessed Lever board is not evidence that the Lever board exhausts its scope ([source-label audit](SOURCE-LABEL-AUDIT.md)).

After the filter guard, spend at most one guarded render on the best explicitly linked, company-bound, apparently loading listing, within the existing total render/fetch and deadline budgets. Keep the normal network/robots restrictions. Record static and rendered body signatures plus exact posting-URL identities in candidate evidence; only a meaningful changed listing body and at least three distinct plausible posting URLs, including validated `JobPosting` entries where present, on that destination can promote it to existing `listing_html`/`listing_jsonld` confidence. It must also have no deeper declared complete-listing link and no visible filter. A spinner, body text alone, static zero, plausible URL path or verified API on a different domain must not raise confidence. This is *source identity* evidence; the subsequent worker scan must still prove listing completeness.

Held-out checks: Datadog, Cloudflare and Zapier-shaped rich static shells hydrate into role links on the linked all-jobs URL; loading text without roles stays at 0.5; Spotify-shaped filtered zero does not become an empty complete source; a featured-roles landing page with an All Jobs link does not auto-accept the featured page; rendering failure or denied requests preserve confirmation/unavailable state. OpenAI's labelled listing has previously yielded roles when extraction started directly there, but discovery's HTTP path was refused. One guarded browser attempt is reasonable only when a first-party explicit listing link led there; if it still refuses or yields no verified roles, do not auto-accept.

## Priority 3: retain explicit-anchor provenance across vendor boundaries

Candidate evidence is currently a free-text `via` string. A probe that redirects across domains is deliberately weakened to `ats_probe` 0.7 in `crossedDomainFromProbe` and `renderAndScan` (`packages/core/src/discovery/discover.ts:361–365, 411–425`); keep that defence. Netflix's company-owned [careers landing page](https://jobs.netflix.com/) explicitly links a custom Eightfold destination, while the observed Eightfold alias still receives 0.7 confirmation. `eightfoldFromUrl` recognises `.eightfold.ai` hosts or API paths, but not an arbitrary custom-domain `/careers` URL (`packages/core/src/ats/tier2.ts:101–112`).

Carry typed hop provenance into the *selected candidate*: *first-party anchor with exact destination*, *HTTP redirect*, *blind probe*, *sitemap* and *network API request*. Preserve the linking page/body signature and exact anchor so a later redirect cannot relabel a guessed board as officially linked. An explicit company-owned link to a vendor/custom board may gain `ats_link` confidence only after the adapter verifies the feed and its company identity; a redirect, guessed slug or mismatched/unnamed board remains below 0.85. Do not promote the old Spotify Lever board on slug or role-count evidence alone. Held-out checks: a Netflix-shaped official anchor plus verified company-bound Eightfold API resolves; the same API discovered only through a cross-domain probe redirect stays confirmation; an unrelated vendor board, embedded partner jobs and a company-name mismatch never auto-accept. Preserve the corrected Netflix label as a source-identity decision, not a posting-recall proof.
