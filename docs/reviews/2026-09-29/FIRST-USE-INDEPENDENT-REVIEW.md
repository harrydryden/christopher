# Independent first-use and recovery review — 29 September 2026

This is a read-through of the current settings, Roles, gate and worker call chains against [the scripted local first-use evidence](FIRST-USE-LIVE-VERIFICATION.md). It is not a second browser run, an unaided user session or a paid-AI check. The production code was frozen for integrated suites during the initial review; the two focused interface corrections below were then authorised separately.

The corrected first-use path is coherent for the observed account: a fresh confirmed member saves keywords and locations together, follows Render, receives 17 account matches from 40 genuine source postings, and sees **“AI scoring unavailable; review manually”** with no model call. The combined initial form and server-side first-save rule prevent an untouched default `operations` gate from masquerading as the person's choice (`GateSetup.tsx`, `app/actions/settings.ts`). Later field saves and suggestion acceptance merge under the same account lock. `scan.ts` now marks only eligible unscored account–role pairs unavailable when AI is disabled, without overwriting a score or skip. `role-workflow.ts` opens Matched when both Matched and Shortlisted are empty, so a successful zero-match observation exposes an explanation and a preference recovery link. Those are substantive J1/J8 gains, but the account was inserted as already email-confirmed and the journey used scripted browser actions on one source.

Two further defects were found by following the current render/query paths:

1. **Scoped empty copy could assert another company's success.** The global Roles company filter includes paused subscriptions (`apps/web/lib/queries/companies.ts:237–245`). The table counts are scoped to that selected company, while the first version of `RoleWorkspace.tsx` used account-wide `setupStatus` to say “A complete scan has finished”. With active company A successfully scanned and paused company B never scanned, selecting B showed that misleading complete message. The concurrent interface correction now suppresses account-wide completion copy for a selected company and links to that company's status; it does not invent a B scan. A scoped-monitoring fact query could later give a more specific state.
2. **Late scores could remain invisible in an open Roles tab.** The Roles poll previously watched only company, gate and import tasks. `scan_company` commits and queues personal `score_job` work; when the scan task ends, the Roles poll could unmount while fit values were still pending. A provider batch also completes its individual `score_job` tasks when handing them to `poll_score_batch`. The authorised narrow fix in `apps/web/lib/work-status.ts` now treats this account's queued/running score, rescore and batch-poll tasks as active, retaining the existing version fingerprint for account-visible rows. Companies remains independent of personal scores. Future batch waits use `AutoRefresh`'s unchanged 10-second-to-one-minute backoff and hidden-tab pause. An isolated PostgreSQL regression covers scan finished → late score, account isolation, rescore ownership and a future batch hand-off; **16/16** [focused tests](implementation-evidence/work-status-score-refresh-test.log), [web typecheck](implementation-evidence/work-status-score-refresh-typecheck.log) and diff check passed. The full integrated suite and final build are parent-owned gates.

One narrower **unresolved no-AI status caveat** remains. A scan's direct fan-out records `unavailable` immediately, but gate re-evaluation (`packages/db/src/gate.ts:223`) and description refresh (`apps/worker/src/handlers/description.ts:163`) call `queueScoring` without an AI-admission decision. That function marks the view `queued`, so after changing a filter or fetching a description in a no-key deployment, Roles can temporarily say “scoring…” although no model is available. The score handler later changes it to `unavailable`; the final first-use filter-restoration check waited for that worker result, and it does not demonstrate immediate truthful status. There is no evidence of lost roles or a permanently wrong state here. A follow-up should make scoring admission and status consistent across **all** producers, including a configured batch wait, and verify no-key filter changes and description-only roles before and after worker processing. The shared DB queue layer has no AI runtime context, so isolated environment checks in it would be a brittle repair.

The old location-only save could have stored a default `operations` gate for existing accounts. Those rows cannot be distinguished from deliberate `operations` choices; the corrected code properly leaves them alone. Support or user-directed review, rather than an inferred automatic rewrite, is needed if affected live accounts are found.
