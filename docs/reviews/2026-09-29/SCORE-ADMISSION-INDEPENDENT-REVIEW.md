# Independent review of scoring admission

Reviewed 29 September 2026 against the scoring-admission development checkpoint. This is a code and focused-regression review, not a paid-model or representative-user assessment. The parent is running the complete worker integration suite separately.

The principal correction is sound: a web request records exact account–role intent as `requested`; the worker checks current eligibility, model availability and account budget under the view lock before creating score work. The final score handler checks again before a provider call. A no-key path settles as `unavailable` rather than leaving an indefinite “scoring” promise, and abandonment marks a failed state only when no newer request or live score/batch task owns the role. The relevant paths are `packages/db/src/tasks.ts:208–244`, `apps/worker/src/score-admission.ts:34–91`, `apps/worker/src/handlers/abandon.ts:90–134` and `apps/worker/src/handlers/learning.ts:91–167`. Production callers pass single pairs, `reevaluateGate` pages of at most 250, or explicit 250-pair chunks; no observed caller exceeds admission's bound.

I raised one material issue during review: after a collector submitted an AI provider batch, it completed the original `score_job` while a `poll_score_batch` task owned the same account–role pair. A later Apply/Undo or rescore could enqueue another `score_job`, potentially paying the model twice. There was also a hand-off window between provider submission and committing the poll task. The final fix checks active poll records **at score execution**, matching the pair and exact scoring-input fingerprint (`learning.ts:149–159`). The queue holds a same-key follow-up behind the original running task; the poll task and original completion commit together (`score-batch.ts:203–208`), so the follow-up sees the poll record once it can start. A changed fingerprint may be scored separately; the older batch result is subject to the existing freshness check on write (`learning.ts:185–213`). The owner added a focused regression that proves same inputs call no model and changed inputs do (`learning-signals.test.ts:497–513`). The guard treats malformed/non-array batch items as empty rather than throwing. This resolves the duplicate-call finding at the tested boundary; it does not establish provider delivery or billing behaviour in production.

The same-input retry-only pass starts only if at least one open, unarchived, eligible view marked `unavailable`, `budget` or `failed` has no active score task. The subsequent rows query includes all views with those retryable states that meet the eligibility rules; it does not filter each row by active-task presence. Existing queue deduplication and the score handler's fingerprint check govern those pairs (`learning.ts:573–609`). A pass that could queue no model work because of availability or budget does not record a `queued` result as if it were a completed rescore (`learning.ts:615–632`). Explicit Apply/Undo requests use their own durable `admit_scores` payload and are not filtered by this automatic retry-only path (`apps/web/lib/decisions.ts:125–170`; `tasks.ts:208–244`). The owner's focused regression covers no-key recovery, then failed-work retry with unchanged inputs (`learning-signals.test.ts:515–530`). I found no concrete dropped explicit update in this path.

I repaired four pre-existing end-to-end test assumptions without weakening their intended checks. One no-key test now expects the skipped role's truthful `decided` state. Three tests that intentionally assert score jobs use an enabled-model fixture for the scan/description arrival; they still assert once-only queuing after description, the 29-follower gate fan-out and a shortlisted role's fresh score (`apps/worker/src/e2e.test.ts:1028–1066, 2340–2362, 2445–2492`). Those **four targeted tests passed, 4/4**, on the dedicated local `ava_applications` database with no paid model. The backend owner reported **30/30 focused score-admission and learning tests**, **2/2 scan ownership fixtures**, and a worker typecheck pass. I inspected those regressions; I did not rerun the whole worker suite. The full-suite outcome must be reported from the parent's separate run.
