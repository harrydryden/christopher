# Historical score recovery: independent review

Reviewed the separate historical-orphan sweep at the shared 29 September 2026 development revision, without editing its implementation: `apps/worker/src/score-orphans.ts`, its six database tests, the `maintainHistory` call, and migration `0049_waiting_score_reconciliation.sql`. This review does not treat my batch hand-back change as independently reviewed.

The sweep changes only `score_state` and `score_state_at` on old `requested` or `queued` views; it does not queue AI work, spend budget or replace a saved fit score. It recognises null legacy timestamps and otherwise waits ten minutes. The ownership check matches the **same account and job** in active admission, live score or provider-poll tasks. It excludes owned rows before its 200-row limit, takes `user_jobs` locks with `SKIP LOCKED`, then rechecks tasks in a second statement at explicitly requested `READ COMMITTED` isolation before writing `failed` ([implementation](../../../apps/worker/src/score-orphans.ts#L28-L64)). This protects a new request that held the view first and allows a later one to supersede a repair. The short statement and lock timeouts, run budget and error result bound a failed pass rather than holding maintenance indefinitely ([implementation](../../../apps/worker/src/score-orphans.ts#L46-L86)).

The hourly maintenance path calls the sweep after task retention, so a pruned historical task can be repaired in the same run ([maintenance](../../../apps/worker/src/maintenance.ts#L122-L142)). The partial index covers waiting states in oldest-first order, including null timestamps ([migration](../../../packages/db/drizzle/0049_waiting_score_reconciliation.sql)). A normal, non-concurrent index build on a large production `user_jobs` table can hold write locks during deployment; this remains a release-planning check, not a defect observed in the disposable database. If the worker is stopped or the hourly claim was recently spent, the repair waits for the next eligible maintenance pass; it is not an immediate page-load repair.

The independent database run used `TEST_DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55439/ava_applications pnpm --filter @ava/worker exec vitest run src/score-orphans.test.ts`: **6/6 passed**. The cases cover missing/done/failed tasks with preserved scores, null timestamps, active ownership and a different account on the same job, recent and already-scored states, 205 active rows ahead of 25 orphans, a locked producer view, and a task committed between selection and the final update ([tests](../../../apps/worker/src/score-orphans.test.ts#L35-L141)). `pnpm --filter @ava/worker typecheck` passed with these sources. The forced interleaving uses a test proxy that currently discards the transaction's isolation option; the production call explicitly sets `READ COMMITTED`, while the test connection uses PostgreSQL's default. Forwarding that option would strengthen the test harness, but its current result still exercises the second-snapshot check.

**Recommendation:** accept this as a bounded repair for historical misleading waiting labels after the full integrated suite and migration check pass. Keep the existing J8 robustness score at **4/5** and overall J8 at **83/100** for now. Six scripted database cases and a local migration do not establish hosted worker uptime, provider-batch recovery under operational interruption, or the broader exception matrix needed for a higher product score.
