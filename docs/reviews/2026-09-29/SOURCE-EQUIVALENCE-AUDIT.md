It does not change the frozen acceptance labels or qualify posting quality. The browser observations used Playwright on the two company-owned pages and read ordinary rendered `<a href>` values. For Cloudflare, the visible consent dialog was declined before clicking the real load-more control. The separate feed enumeration used a direct unauthenticated HTTP GET and Python standard-library JSON parsing of the public `jobs` array; Zapier's comparison included only `isListed=true`. No AVA discovery, extraction or acceptance parser produced either reference set. The first-party pages' own matching API requests are stronger provenance than a guessed vendor-domain redirect: these feeds supplied the listings observed in this session.

The retained raw files are [Cloudflare's feed](implementation-evidence/source-audit/cloudflare-greenhouse-equivalence.raw.json), [Cloudflare's fully rendered HTML](implementation-evidence/source-audit/cloudflare-official-rendered-equivalence.html), [Zapier's feed](implementation-evidence/source-audit/zapier-ashby-equivalence.raw.json) and [Zapier's rendered HTML](implementation-evidence/source-audit/zapier-official-rendered-equivalence.html). Their bytes and hashes are in the comparison JSON. The earlier Zapier raw hash happens to be unchanged from the 13:29 UTC snapshot; this audit compares it with a **fresh** first-party browser render and matching browser response.

This is machine-enumerated identity equivalence for the two visible listings at capture time. It does not establish whether each posting is genuine/current in a human review, whether a company publishes roles on another channel, whether the feeds will stay equivalent, or whether the product can select and extract them reliably. A reviewer should adjudicate alias labels separately from posting-precision and recall gates.
