# Discovery, filtering, learning and reliability review

Reviewed 29 September 2026 against `main` at `ebb346b`. The job statements in `docs/UX-JOURNEYS.md` provide the user outcomes; current code, `docs/SPEC.md` and current release evidence determine implementation status. Scores below are judgement on the present product, not a claim of production acceptance. No database tests or live provider calls were run for this review.

## Findings, ordered by user impact

1. **Release blocker — independently labelled discovery acceptance is still open.** SPEC §9 requires at least 80% of the golden set to resolve automatically at confidence ≥0.85, zero wrong sources automatically accepted, and posting identity recall/precision thresholds. The latest full browser-enabled 25-case observation (`docs/live-acceptance-browser-full-final-2026-09-20.json`) reports 60% labelled automatic agreement and no posting-identity labels; the earlier release candidate reports one wrong automatic acceptance. Narrow fixes for Stripe/Mozilla and a six-source machine-derived frozen oracle improve evidence but do not replace the required human-reviewed golden set. `docs/live-acceptance.md` explicitly distinguishes those claims. **Outcome:** a person can follow the wrong or incomplete listing and receive an apparently healthy but incomplete table. The report was produced under bounded local conditions, so this is an *unpassed gate*, not proof that the present production path misses 40% of companies. Gate: a dated 25-company independently reviewed set with ≥8 ATS types, ≥5 custom HTML sources, JavaScript and protected cases; freeze and enumerate posting identities; run full production discovery and extraction; achieve every SPEC §9 threshold, with zero high-confidence wrong-source acceptances.

2. **P1 — a suspect empty scan can disappear from actionable Health.** `apps/worker/src/handlers/scan.ts:921` queues re-discovery for `suspect_empty` while leaving a source active unless it has reached the failure threshold (`:905-909`). `apps/web/lib/queries/health.ts:1328-1347` constructs attention only from an unconfirmed, blocked or failing source, no working source, or a latest discovery run with candidates needing confirmation. The sidebar count uses the same limited cases (`:1395-1406`). If re-discovery finds nothing or fails, a still-active source with a suspect empty observation earns no *Needs you* item or count. It is visible lower down as a recent problem scan (`apps/web/app/(app)/health/page.tsx:80`), but SPEC R-9.1 promises suspect empties in the attention list. **Outcome:** a follower may overlook a vanished listing while the company retains a normal active badge. Gate: keep the latest unresolved suspect empty (and persistent partial shrink) as one company attention item until a successful complete scan or deliberate source resolution; assert item/list/count parity for `suspect_empty → not_found` and `suspect_empty → failed`.

3. **P1 — concurrent filter acceptance can lose a chosen term.** `apps/web/app/actions/learning.ts:145-155` reads a gate and prepares the replacement before `saveSettingsAndGate` takes its serialisation lock (`apps/web/lib/settings.ts:76-85`). Two near-simultaneous Accept actions can both read the same old gate; the second saves a whole gate containing only its own new term. Both suggestions can then be marked accepted (`learning.ts:169-180`), while only one term survives and its roles remain outside the table. The existing integration coverage at `apps/web/app/actions/learning.integration.test.ts:85-97` exercises sequential acceptance, not this interleaving. **Outcome:** the product says it learned a preference it silently lost. Gate: perform suggestion-state check and gate merge under one per-account transaction lock, re-read the latest settings inside it, and add a concurrent two-term acceptance regression that verifies both stored terms and membership.

4. **P2 — homepage corrections do not fence in-flight discovery.** `apps/web/app/actions/admin.ts:46-54` can change a shared company's homepage while an existing discovery task is fetching the old one. `apps/worker/src/handlers/discover.ts:70-75` reads the company once, and `:127-160` persists the resulting source and queues a scan without rechecking its homepage under the transaction. The logo path has exactly that guard (`discover.ts:175-188`), showing the distinction. **Outcome:** an administrator can correct a mistaken domain, yet a late task can attach the former site's careers source to the corrected company for every follower. Gate: carry the starting homepage into `recordResult`, lock and compare the current homepage before any source/name/run changes, and test an edit that lands while discovery is in flight.

5. **P2 — learning's visible acceptance is stronger than its measured quality.** `apps/web/app/(app)/learning/page.tsx:201-224` correctly withholds calibration until 20 decisions and displays bucket sizes. SPEC §9 calls for ≥75% agreement after 50 real decisions. No report here supplies a real-decision calibration sample or an independent ranking judgement; the release evidence focuses on discovery, extraction and CV evaluation. **Outcome:** the score can look authoritative before there is evidence that it tracks this account's choices. Gate: enrol consented, real 50-decision cohorts, report high-score apply and low-score skip rates with denominators, disagreement examples and model/version, then adjust prompts or positioning if either bucket misses 75%. This is an evidence gap, not a demonstrated scoring defect.

## Missing jobs and next acceptance sequence

The canonical journeys understate three jobs that determine whether a person can trust this product: **prove that a source is the complete listing**, **recover a company after a source silently empties or changes domain**, and **know whether a deployed release and backup can actually restore service**. Treat these as explicit jobs, with the following gates in order:

1. Fix the two reproducible state bugs above: Health must raise unresolved suspect empties; accepting two terms concurrently must preserve both. Fence discovery against homepage changes. Add targeted regressions, including the user-visible list/count/term outcomes.
2. Complete the independent golden set and rerun full discovery/extraction against dated, frozen source identities. Keep the machine-derived 2,419-posting replay as regression evidence, not a substitute for human labels (`docs/live-acceptance.md`).
3. Exercise a hosted daily run and provider failure cases at the 100-user target. Establish elapsed scan time, queue age, failure visibility and browser heap headroom under real host pacing. The local 50-company and synthetic 100-user reports are useful capacity evidence with explicit limits (`docs/benchmarks/fifty-company-daily-run-2026-09-20.json`, `docs/benchmarks/hundred-users-http-soak-2026-09-20.json`).
4. Require a green CI run and release identity check for this exact commit before claiming release readiness. The 20 September `final-checks` record itself says `productionReleaseAccepted: false` and `hostedCapacityGate: open`; operational monitoring can be green while CI/release is not. Prove delivery of a failed operational alert to Harry, connect an isolated restored database to the application and worker, and rehearse rollback within the agreed four-hour recovery objective (`docs/RELEASE-GATES.md:125-153`).
5. Measure learning on real decisions. Report the calibration denominators, and inspect accepted/rejected company suggestions for relevance and verification drift after people have used them.

At review time, the worker and web health endpoints both reported the exact `ebb346b` commit, and the operational-status workflow passed. The present evidence supports an advanced local implementation, but no production-wide acceptance claim. A successful local drill, a bounded live observation, a green operational snapshot and a released commit answer different questions.
