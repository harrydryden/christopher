# UX and JTBD review — 29 September 2026

Scope: read-only code review at `ebb346b`, using the six jobs in `docs/UX-JOURNEYS.md` (§§ Journey 1–6) and the current `docs/SPEC.md` as the contract. These are implementation findings, not claims from a live usability session. Scores are 0–5: **completeness** = how much of the job the product lets someone finish, **robustness** = how well the path handles waiting, refusal and correction, **UX** = clarity and effort in the interface. A 5 requires a reliable end-to-end path that is clear on a phone and to keyboard users. Runtime, database and assistive-technology outcomes still need direct verification.

## Overall judgement

The product has moved substantially beyond the September journey audit. The canonical document now explicitly says Waves 1 and 2 were built (`docs/UX-JOURNEYS.md`, Status after § Sequencing). The current code includes a five-step checklist, chosen-before-scan gate, company setup timeline, evidence-rich role review, optimistic decisions with Undo, priced CV controls, Library document import and evidence scores, and a single applications pipeline. Treating the document's historical “Today” paragraphs as present defects would be inaccurate. The strongest remaining issue is not missing features but **the trustworthiness and usability of the last mile**: an empty Roles page can state a false reason for emptiness; the Library's phone layout still has a wide evidence table; and dates and next actions in the pipeline do not govern its ordering.

## Priority findings and acceptance criteria

### P0 — Make first-run truth and Library phone editing dependable

1. **The empty Roles explanation can be false.** `Setup` displays the checklist whenever all role counts are zero, independently of scan state (`apps/web/app/(app)/page.tsx:35–40`), and the unconditional sentence is “Nothing has run yet” (`apps/web/lib/setup.ts:55–57`). A company can have completed a successful scan with zero matching roles; a person who has not filled the Library can still see this false explanation indefinitely. The checklist's five facts have no scan or source-read milestone (`apps/web/lib/setup.ts:72–125`), although Journey 1 defines “done” as a first scan having run against chosen filters (`docs/UX-JOURNEYS.md:46–51`). **Accept:** distinguish not scanned, scanning, scan succeeded with zero admitted roles, and scan failed/needs attention in the empty state, using the account's followed-company scan data. The completed setup state should confirm what actually happened and link to filters or Health when zero roles remain. Do not mark the first-run journey complete solely because five inputs were saved.

2. **The Library's responsibility editor still forces a wide table on a phone.** Employment history has a stacked layout below `md` (`apps/web/components/EmploymentHistoryTable.tsx:48–96`), but each job's evidence uses an `overflow-x-auto` table at `min-w-[820px]` (`apps/web/components/CvLibraryEditor.tsx:366–418`). Its six columns put narrative text, confirmation, type, score and Remove on different horizontal positions; the Save bar sits above the long editor (`CvLibraryEditor.tsx:269–287`). Horizontal travel makes reviewing one evidence row cognitively expensive, particularly while confirming or tagging many rows. **Accept:** below a suitable breakpoint, render each responsibility as a single labelled card with narrative, confirmation, type, score and removal visible in reading order; preserve the same state and validation as desktop, without horizontal scrolling at a 320–390px viewport.

### P1 — Reduce friction in the repeated jobs

3. **The UI no longer exposes the supported multi-company paste.** The `addCompanies` action deliberately parses newline/comma-separated URLs and bounds the submission (`apps/web/app/actions/companies.ts:86–98`), matching R-1.4 (`docs/SPEC.md:187`), but the only `urls` form in the current app is a hidden field populated from one search query on Discover (`apps/web/app/(app)/suggestions/page.tsx:72–100`). The setup milestone asks the person to follow three companies (`apps/web/lib/setup.ts:99–107`), so a person with three known URLs must search/add each separately. **Accept:** offer a clearly labelled “Paste several homepages” textarea on Discover or Companies, explain the cap, return added/followed/skipped outcomes, and retain the existing one-at-a-time catalogue search.

4. **An application date is prefilled even when the user is recording another status.** Every status except Applying requires `appliedOn`, defaulting to `row.application?.appliedOn || today()` (`apps/web/components/ApplicationsTable.tsx:145–156`); `today()` uses UTC (`ApplicationsTable.tsx:61–62`) rather than the user's calendar date. A user moving a shortlisted role directly to Rejected, or entering an old interview, can save today's date as a claimed application date without having supplied it. Near local midnight, the default can be the wrong local day. **Accept:** only ask for an application date when the user says one exists; do not silently manufacture it when recording later statuses; default from a local calendar date where a default is appropriate. A status change with no submitted application must remain truthful in both the row and history.

5. **Urgent next actions have no working view.** The page shows a due summary (`apps/web/app/(app)/applications/page.tsx:63–92,127–140`) and a next-step line per row (`apps/web/components/ApplicationsTable.tsx:402–410`), but the pipeline offers only Active, Closed and All (`apps/web/lib/queries/applications.ts:54–55`) and sorts by stage rank before `updated_at` (`apps/web/lib/queries/applications.ts:611–639`). On a multi-page pipeline, an overdue action may be on a later page, behind many rows at an earlier stage. **Accept:** provide a “Due/overdue” view or explicit sort that places dated next steps first across the account, with a link from the due summary; show overdue count and retain company scope. A next step due today should be findable without paging through unrelated stages.

6. **The Health count is one step away from its destination.** A count of attention items is attached to Settings (`apps/web/app/(app)/layout.tsx:25–35,67–77`), but Settings opens Preferences, and Health is a secondary link shown only within the group (`apps/web/components/WorkspaceNav.tsx:6–15`). `NavLink` describes the number on hover/to assistive technology (`apps/web/components/NavLink.tsx:27–43`), yet a sighted user sees “Settings 3” without the word “Health”. **Accept:** make the count's label and target explicit, either with a direct Health entry or a clearly named Health link in the global shell. One activation from any page should open the actionable list.

### P2 — Improve scanability and recovery

7. **The three primary work tables remain desktop-shaped on phones.** Shared `Table` enforces `min-w-[720px]` with horizontal overflow (`apps/web/components/table.tsx:3–8`); it is used by Roles (`apps/web/components/RolesTable.tsx:879–927`), Companies (`apps/web/app/(app)/companies/page.tsx:82–168`) and Applications (`apps/web/components/ApplicationsTable.tsx:359–435`). The last action column on Roles and Companies requires horizontal movement after reading the role/company; Applications' status, CV and updated columns similarly separate the decision from its context. **Accept:** at phone widths, preserve company/role, status, fit or next action, and the primary action in one vertically readable item; test with long names and 200% text zoom. The full desktop table can remain at larger widths.

8. **The undo window is only five seconds and holds one decision.** A new decision replaces the previous notice and clears its timer (`apps/web/components/RolesTable.tsx:22–26,596–606`); the visible Undo is below the table (`RolesTable.tsx:813–817,927–932`). In a fast review session, one more decision removes the previous quick recovery path. Reset/Reconsider still exists in the decided tabs (`RolesTable.tsx:383–394`), so this is a speed/recovery issue rather than data loss. **Accept:** keep recent decisions individually undoable for a longer, clearly announced interval, or make the notice link directly to the decided row after expiry; verify pointer, keyboard and screen-reader access after optimistic removal.

9. **The application stage overview is informative but not navigational.** Stage counts are plain spans (`apps/web/app/(app)/applications/page.tsx:115–127`) and stage meanings are in a collapsed disclosure (`ApplicationsPage.tsx:166–176`). Because the table is stage sorted and paged, clicking a count cannot currently take someone to Interview or Offer. **Accept:** make stage counts links or filters with a clear selected state, and surface the meaning where stages are acted on; keep Active/Closed/All as broad segments.

10. **The responsive employment form duplicates required controls.** Desktop inputs are under `hidden md:block` and phone inputs under `md:hidden`, but both sets contain required company/title fields (`apps/web/components/EmploymentHistoryTable.tsx:51–83`). This adds two validation targets for each fact. In a Chromium mobile check at 390px, an incomplete new job **did** focus the visible title field on Save: the editor's `onInvalidCapture` switches panels and focuses the invalid control (`apps/web/components/CvLibraryEditor.tsx:214–218,332–338`). The predicted save blockage did not occur in that check. No clear inline validation explanation was observed. **Accept:** have one validation target per fact where feasible, or verify visible focus and an announced, field-specific error across mobile/desktop browsers and screen readers. This is an accessibility hardening item, not a confirmed blocking defect.

## What is working well

- **Onboarding and company setup have meaningful direction.** The checklist derives progress from account data and links to exact fields (`apps/web/lib/setup.ts:72–125`); company discovery distinguishes queued/running, candidates and not-found and offers recovery inline (`apps/web/app/(app)/companies/[id]/page.tsx:253–322`); elapsed and expected timing are in the company timeline (`apps/web/components/CompanySetupTimeline.tsx:15–57`). Verification is stated beside blocked controls (`apps/web/app/(app)/layout.tsx:54–61`; company page `:141–143,283–290`).
- **Role review shows evidence rather than a bare score.** Keyword chips, location reason, fit verdict/rationale, salary and stored description appear in the expanded panel (`apps/web/components/RolesTable.tsx:323–368`). Decisions have required skip reasons, quick reasons, keyboard shortcuts, optimistic feedback and reset/undo paths (`RolesTable.tsx:173–225,383–405,639–779,813–817`).
- **CV work exposes its cost and limitations.** The role panel offers a priced build and explains a refusal (`apps/web/components/RolesTable.tsx:87–116`); the CV page shows the build total in its header, the source of the advert, an evaluation panel and an explained finalise obstacle (`apps/web/app/(app)/cv/[id]/page.tsx:47–64,141–166,187–249`). Sharing and comments are present (`CvDraftPage.tsx:168–175,326–340`).
- **The Library supports both starting and improving.** PDF/Word, paste and personal-site imports are explained up front (`apps/web/components/LibraryImportCard.tsx:18–68`); the editor has unsaved-change protection and a visible Save/Re-score bar (`apps/web/components/CvLibraryEditor.tsx:153–180,269–299`), per-job readiness and evidence prompts (`CvLibraryEditor.tsx:339–363`), and an obsolete-edit merge path (`CvLibraryEditor.tsx:189–212`).
- **Tracking has a coherent data shape.** One Applications page carries statuses, CVs, dates, notes and next actions (`apps/web/components/ApplicationsTable.tsx:72–202,324–435`); backward moves ask for confirmation (`ApplicationsTable.tsx:81–112`), and pipeline pagination happens in SQL (`apps/web/lib/queries/applications.ts:617–666`).

## Roadmap and validation

1. **First reliability pass:** correct the empty-state and setup-completion logic (1) and fix application-date semantics (4). These are trust issues and deserve acceptance checks before visual polish.
2. **Phone-first repeated flows:** make Library responsibilities usable without horizontal scrolling (2), then Roles/Companies/Applications (7). Test 320px, 390px, 200% zoom, long role titles, keyboard-only operation and a screen reader on the expanded rows. A code-only pass cannot certify those outcomes.
3. **Workflow speed:** restore visible multi-company entry (3), add due/overdue navigation (5), link Health directly (6), then improve undo and stage navigation (8–9). Measure time to follow three employers, review ten roles and locate one overdue interview against the current flow.

This review did not run database suites or modify the application. A separate Chromium mobile check at 390px tested one incomplete Library save as noted in finding 10; broader browser/device verification remains an acceptance gate.

## Visual language and task simplicity: a further pass

The design language is unusually consistent. One green chrome, black/white surfaces, status hues with words, squared borders and restrained stepped motion are defined centrally (`apps/web/app/globals.css:24–76,128–173`; `docs/DESIGN-SYSTEM.md:19–25,120–155`). `Button`, `Card` and `PageHeader` repeat that structure rather than inventing new shapes (`apps/web/components/Button.tsx:12–46`, `Card.tsx:19–29`, `PageHeader.tsx:12–20`). Focus has a single visible ring and reduced motion turns animations off (`globals.css:223–229,331–336`). Library score guidance is a click-open panel with deliberate Escape/focus behaviour, rather than an inaccessible hover tooltip (`apps/web/components/RowScoreButton.tsx:9–25,47–65,74–122`); the Type menu has arrow-key movement (`apps/web/components/LibraryRowTypeMenu.tsx:72–94`). These are genuine strengths.

The following design principles would preserve that identity while making the product easier to use:

1. **Let meaning outrank compactness at decision points.** The system's 9px badges/table heads, 10px small buttons and 11px navigation are intentional (`apps/web/app/globals.css:133–155`; `apps/web/components/Badge.tsx:33–50`; `apps/web/components/table.tsx:30–34`). Yet the small `Button` is roughly 26px tall from its own 10px line height, 4px vertical padding and borders (`apps/web/components/Button.tsx:12–29`), below the design system's own 44px target (`docs/DESIGN-SYSTEM.md:130–133`). Some high-frequency controls add `min-h-11` explicitly (`apps/web/components/SuggestionDeck.tsx:259–262`), showing a workable precedent. Give primary row actions and all touch controls at least that target; keep small pixel type for non-interactive metadata and test whether table headings and navigation remain readable at normal distance. This is a usability risk inferred from CSS, not a measured contrast failure.

2. **Show every active constraint before a result.** The Roles filter form hides Location, Min fit and sort inside a closed `details` whose summary is always just “More filters” (`apps/web/components/RolesFilterBar.tsx:79–117`). A filtered-out table can therefore look empty while its cause is invisible. Show active criteria as removable chips or a count on the summary, preserve them across tabs, and offer one visible Reset. A person should be able to explain an empty result without opening an unknown drawer. The same rule applies to CV finalisation: its prominent `/100` match score appears before the essential-gap and factual-concern counts (`apps/web/components/CvAssessmentPanel.tsx:115–138`); ensure those blocking facts are read together with the score, not discovered after it.

3. **Use one clear level for each kind of feedback.** The global scan strip, confirmation banner, setup checklist, filter-suggestion strip and role tabs can all stack before the first role (`apps/web/app/(app)/layout.tsx:48–92`; `apps/web/app/(app)/page.tsx:60–68`). A separate 390px Chromium check found navigation plus status using about 292px of vertical space and the first role starting below 844px after header, setup, suggestions, tabs and filters. Each element is useful alone, but the arrangement gives routine status, setup work and urgent action similar visual weight. Keep the scan strip terse; promote only the next required action or a failure to a prominent notice; put passive background progress in context on its owning company/CV page. **Accept:** on a 390px first-run Roles page, show the current setup action and the first role or truthful empty explanation within the first viewport and one short scroll, without hiding a refusal. Preserve announced action failures: `RefusalNotice` uses `role="alert"` (`apps/web/components/RefusalNotice.tsx:10–17`), whereas the shared `SettingsForm` renders a failed save as an unlabelled paragraph after the fields (`apps/web/components/SettingsForm.tsx:30–41`). Give shared form errors an announced status/alert, associate them with the affected field where possible, and move focus or provide a summary when submission fails. Avoid making every routine poll result a live announcement.

4. **Keep focus and context when an item disappears.** Role shortcuts move a visual `highlightIndex` and scroll a cell into view, but they do not move DOM focus or expose an active descendant (`apps/web/components/RolesTable.tsx:579–584,749–773,783–795`). Saving a decision removes its row optimistically (`RolesTable.tsx:649–670`); Escape from the reason box explicitly blurs its current target (`RolesTable.tsx:730–742`). This may leave a keyboard or screen-reader user without a meaningful current item even though the visual cursor appears to advance. Preserve the quick keyboard path while making the active row programmatically identifiable; after a saved decision, focus the next review control or the Undo notice; after Escape, return focus to the row's Review control. Verify this with actual keyboard and screen-reader runs, not just DOM assertions.

Native `window.confirm` is used for application regressions, Library discard/navigation and company management (`apps/web/components/ApplicationsTable.tsx:81–112`; `CvLibraryEditor.tsx:153–180,255–260`; `CompanyManageMenu.tsx:62–66`). It has the benefit of a familiar, blocking confirmation, but the app should reserve it for genuinely consequential changes and say the specific consequence before the choice. The existing company menu does this well for Hide and Stop following (`CompanyManageMenu.tsx:87–100`). No custom modal system is needed merely for visual consistency.

### Ideal paths and measures for the six jobs

The measures below are proposed usability targets for moderated tests with a new account and realistic, seeded data; they are **not** measured results. Count an action as a click, tap or submit; exclude typing and the external employer's own application form. Test one desktop keyboard-only session and one 390px touch session for each path, and record failure/hesitation points in addition to timing.

| Job | Concrete ideal flow | Proposed test measure |
|---|---|---|
| 1. Onboard | Confirm address → choose keyword/location gate → add three known employers in one paste → see each discovery/scan state → see first matching roles or a truthful zero-match explanation → import/review Library evidence when ready to build. | At least 4/5 participants correctly state whether the first scan ran and why Roles is empty; all complete the three-employer setup without needing help; count page changes and time to a trustworthy first result. |
| 2. Follow companies | From Companies, paste or search → follow → watch source confirmation and first scan on one company card → resolve a failed source in Health → return to its admitted roles. | At least 4/5 can identify the next required action and the last successful scan within 30 seconds; recovery takes one destination change from the attention item; no one mistakes queued, failed and zero-match states. |
| 3. Review roles | Open Matched → expand one row → read keyword/location/fit/description → shortlist or dismiss with a reason → see where it went and Undo if mistaken → continue to next row without losing focus. | Median ≤45 seconds per role after the first, with no blind decisions attributable to missing evidence; all keyboard participants can find their active row and reverse a deliberate mistaken decision. |
| 4. Make application | Open shortlisted role → see estimated price and Library readiness → build → understand progress → inspect essential gaps/factual concerns alongside score → edit or add evidence → reassess → finalise, preview and share/record. | At least 4/5 can name the blocker to finalisation and the next corrective action within 30 seconds; no participant interprets a high score as permission to finalise with factual concerns; record build-to-finalised elapsed time separately from worker wait. |
| 5. Improve Library | Import CV → review proposed items → complete one job's evidence on a phone → confirm/tag rows → save → understand readiness and optional Re-score → recover an intentionally obsolete save. | All can save one complete job without horizontal panning or validation confusion; at least 4/5 can explain confirmed versus scored evidence; no entered text is lost in the obsolete-save exercise. |
| 6. Track applications | Open Applications → find a due action → update the stage with its actual event date → set the next action → open the saved CV/PDF and history → return to the same row. | At least 4/5 find a due/overdue action within 15 seconds in a seeded 60-row pipeline; no one records an untrue application date; all can identify what was saved today versus when the event occurred. |

The current component tests do exercise role interactions, suggestion cards and score-panel ARIA behaviour (`apps/web/components/RolesTable.test.tsx`, `SuggestionDeck.test.tsx`, `RowScoreButton.test.tsx`). They do not substitute for the proposed focus, touch and comprehension sessions; the targets above are release checks for those behaviours, not promises inferred from the code.
