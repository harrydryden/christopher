# Location evidence and score publication — 1 October 2026

This local development checkpoint follows commit `35302ca` and the [Workday enrichment verification](WORKDAY-LOCATION-VERIFICATION.md). Astra directed the consistency and concurrency review; Sol agents implemented the changes and checked them. It does not qualify a production release or increase any JTBD score.

## Defects and changes

The previous checkpoint resolved the employer's 70-location list, including Boston, but downstream paths disagreed. The roles table displayed every location at once, CSV exported only the primary city, A5 fit scoring received only that city, and new decision snapshots likewise retained only the primary city. A Boston match could therefore become an Atlanta-only export, scoring request or learning record.

The table now keeps lists of more than three places behind a native disclosure; opening it exposes every stored place. Small lists remain inline. The phone card uses its available width. CSV exports the complete list in one safely quoted cell. New decision snapshots retain the ordered list, with explicit uncertainty for pending or unavailable location checks. Previously verified names receive that description only when their verification timestamp exists. Historical decisions are preserved as recorded.

A5 now receives the confirmed employer-listed locations. Canonical ordering and deduplication make its input fingerprint insensitive to list order. A pending or unavailable refresh supplies an explicit verification status instead of presenting retained names as current evidence. Secondary-location changes now trigger fresh scoring. An unchanged weekly confirmation retains the existing score and permits a cache check without another model call. A score or empty response made while locations were unverified is reconsidered when verification succeeds.

An unusually large stored location string can no longer make the decision digest discard all following decisions. The summary explicitly omits oversized location text while retaining the decision, role and reason; the database snapshot retains the full text. This is a summary bound, not a rewrite of historical evidence.

The review also found that a delayed score could arrive after job evidence had changed and overwrite the invalidated result. Both live and batch publication now re-read the scoring inputs and current eligibility. Gate, job and role-view locks serialise publication with changes to those rows. Changed eligible inputs receive a durable follow-up task. Closed, archived, skipped or inaccessible private roles reject the answer. Batch accounting still records a paid response even when its result is stale. Empty responses use the same check; a failed update preserves a previous fit with a failed-update state. Score publication no longer changes the independent legacy hidden flag.

## Remaining limits and re-score

The publication guard is not a universal serialisation guarantee. Profile, Library, decision-digest and non-gate settings changes committed before its re-read are detected, but their writers do not all share the publication locks. A concurrent edit after the re-read remains a separate consistency concern. Timestamp ordering also does not distinguish same-input completions in the same millisecond; changed-input answers are still rejected by the fingerprint check. The publication tests inject changes during the provider delay; they do not exercise two database transactions racing for the row locks. The lock-order guarantee is supported by code inspection. Unchanged weekly confirmation still queues one score/hash check per eligible previously completed view, so avoiding a model call does not remove the database/task cost. The targeted tests do not establish hosted concurrency or throughput.

The A5 system prompt is unchanged, but the role input and some decision summaries have changed. Affected replay recordings require fresh verification. Current-job location input retains all locations; at the adapter's maximum of 1,000 names this can be large, so request cost and context behaviour still need qualification. No paid model call, deployment or production migration was performed for this checkpoint.

Readiness remains **J1 83, J2 77, J3 85, J4 83, J5 85, J6 85, J7 80, J8 83 and J9 70**, with dimensions unchanged in the [canonical scorecard and roadmap](../2026-09-29/RESCORE-90.md). These repairs improve J2/J3 evidence consistency, J7 learning provenance and J8 recovery; they do not establish model judgement quality, posting recall, representative usability or hosted operations. Every-job 90/100 remains unproven, and J2, J7 and J9 still miss dimension floors. The existing live-corpus, independent human review, provider replay, genuine-decision and operational acceptance work remains necessary.
