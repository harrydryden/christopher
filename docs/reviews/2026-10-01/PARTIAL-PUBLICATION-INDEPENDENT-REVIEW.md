# Partial HTML publication: independent checkpoint review

**Scope.** I reviewed migration `0050_html_partial_publication.sql`, the durable checkpoint and scan commit changes, and the account-facing progress contract. I wrote a separate adversarial worker file, `html-partial-publication-adversarial.test.ts`, without editing the scan implementation or its existing end-to-end tests. This is local engineering evidence, not a hosted reliability or posting-accuracy acceptance result.

The implementation now publishes a bounded interval of verified HTML pages before the listing finishes. Catalogue roles and account views, their description or score requests, the page cursor and cumulative new-role count commit together. A continuing claim leaves the terminal scan marker, absence/closure, source success metadata and first-scan completion alone. The first-scan seeding decision persists on the generation. Pages carry fetch-time observation timestamps; existing pages are backfilled from their generation start, while a page written by an old worker without the new column receives a 1970 sentinel that the new worker interprets as the generation start. Newer complete and partial observations fence older positive and absence work.

The independent tests found four material gaps during development. A terminal claim could read only 20 of 21 unpublished old-worker pages, then delete the checkpoint; the repair drains a bounded 20-page interval and defers terminal commit until the tail is published. Continuing claims initially returned before queuing detail and scoring work; those queue writes now join the positive transaction. A newer partial observation did not initially protect a role from an older generation's absence pass; terminal absence now excludes jobs seen since that generation started. Finally, old staged inline text could overwrite a newer description fetched for the same job; the commit now prefers stored text whose fetch time is at least the page observation time. Review also caught an accidental reset of the long-listing flag and an untimed first-page browser fallback; the worker now preserves the flag and applies the generation start as the fallback's conservative observation time.

**Checks run independently.** `pnpm --filter @ava/db typecheck` and `pnpm --filter @ava/worker typecheck` passed. `DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55439/ava_reliability pnpm db:migrate` applied migration 0050 on a disposable PostgreSQL database ([migration log](implementation-evidence/partial-publication/partial-source-migrate-0050.log)). `TEST_DATABASE_URL=postgres://postgres:postgres@127.0.0.1:55439/ava_reliability pnpm --filter @ava/worker exec vitest run src/html-partial-publication-adversarial.test.ts` passed **5/5** ([adversarial log](implementation-evidence/partial-publication/partial-source-adversarial.log)). Those tests cover immediate detail-task creation, a newer partial scan's absence fence, stale staged inline text versus newer fetched text/hash/time, a newer complete scan versus an old-worker page with unknown observation time, and a stop during a blocked positive insert. The last case proves jobs, views, terminal marker and cursor roll back while staged pages remain; resumption drains 20 then publishes page 21 once with one final scan. The observed failures were reported to the implementation owner as they arose, and the final test log records the repaired behaviour.

**Release limits.** The migration is additive, but mixed old and new worker processing of one active checkpoint is not established as safe: old code ignores publication cursors and freshness fences. Apply the migration, stop and drain old workers, start the new worker, then deploy the interface. After a new worker has published pages, an old-code rollback needs a separately tested recovery procedure; pause and roll forward until one exists. The local cases do not measure production host pacing, a 50-company daily run, actual useful-result latency, posting recall or precision on an independently labelled corpus, or whether people understand incomplete progress on phone and keyboard. The separate live observation and usability checks remain open.

**J2 recommendation.** Retain the canonical **77/100** (completeness 4, robustness 3.5, UX/UI 4) until the labelled source/posting corpus and representative user and production checks establish the broader outcome. The code removes a known delay in long listings and the deterministic adversarial cases support its transaction and freshness rules; they cannot justify J2 at 90 or lift its robustness floor on their own.
