# Partial source publication — development checkpoint

Status: implemented and verified locally. This is engineering evidence for the J2 continuation defect, not a 90-point acceptance result or a production capacity claim.

## Resulting behaviour

A continued HTML listing publishes verified positive roles after each bounded page batch. The scan remains incomplete until traversal finishes. Publication creates or updates catalogue roles, applies current account gates, and queues description or scoring work. It does not record a terminal scan, finish the scan run, count an absence, close a role, reset source failure state or mark first-scan setup complete. The final claim records one scan with the cumulative new catalogue-row count.

The publication transaction locks the task's source and generation, reads an interval of at most 20 unpublished stored pages, and commits the role changes with the publication cursor and new-row count. It can also publish positive observations from a current incomplete page or the existing first-page rendered fallback; neither is complete coverage. A task reclaimed after staging can publish stored pages; a task reclaimed after publication starts at the next page. A generation with more than 20 unpublished stored pages left by an older worker drains over further claims before terminal finalisation. Boundary drift or source edits reset the current page cursor without erasing already published historical positives or extending the original expiry/restart limits.

Freshness uses each page's observation time, the role's `lastSeenAt` and the source's `lastOkScanAt` conservatively. An older page cannot overwrite a newer role sighting, adoption or description, and a generation overlapping a newer complete scan cannot infer absence or replace newer source metadata. A later partial sighting likewise fences that role from an older generation's negative pass. The first-scan seed decision persists with the generation across claims and restarts; rows first observed after an intervening complete scan are not labelled as day-one seed rows. An old-worker page with no observation time uses the generation start as its conservative time rather than the database sentinel or publication time.

It covers 20 roles visible before the second claim with no scan row or finished run, final 25-role count, interrupted metrics, source edit and boundary drift, expiry and partial endings, description work at first publication, and a small HTML page admitted through freshly fetched detail text.
- An [independent adversarial group](implementation-evidence/partial-publication/partial-source-adversarial.log) passed **5/5** on `ava_reliability`. It covers transaction abort and retry, a 21-page old-worker backlog, a newer partial observation before an old terminal negative pass, a newer complete scan before an old page, and newer fetched description text surviving delayed staged evidence.
- A [synthetic 25-page browser fixture](../2026-09-29/implementation-evidence/partial-publication/fixture-partial.json) produced **20 jobs and 20 matching account views after the first claim**, with no terminal scan and first-scan setup at 3/4. The [second claim](../2026-09-29/implementation-evidence/partial-publication/fixture-terminal.json) rechecked two boundary pages, fetched five more, then produced 25 jobs/views, one `ok` scan and no generation. At [1,280 px and 375 px](../2026-09-29/implementation-evidence/partial-publication/browser-partial.json), the first 20 roles were visible, the incomplete Health card remained visible, its Review roles link worked by keyboard, and neither page exceeded the viewport width. The [terminal browser check](../2026-09-29/implementation-evidence/partial-publication/browser-terminal.json) showed completed setup. A separate [stopped-worker check](../2026-09-29/implementation-evidence/partial-publication/browser-shared-run-stopped.json) displayed “Scan waiting for monitoring” and a keyboard-operable Health link at both widths. These are local mocked pages and a synthetic account, not representative-user or live-host evidence.

The first implementation exposed three defects during review: continuing publication returned before queuing descriptions/scores, a terminal commit could discard an old-worker backlog beyond its first 20 unpublished pages, and active-duration metrics omitted the new publication transaction. All were repaired and the focused regressions passed. Continuation tests now assert early publication; the source-edit test no longer expects previously published positives to disappear. A frozen test clock was advanced where equal timestamps correctly triggered the conservative freshness fence.

## Scope and rollout limits

The stored-page publication interval is bounded to 20 pages, with the limited additional positive inputs noted above. Existing traversal and final coverage code still reads the bounded full checkpoint prefix (up to 600 pages, 3 MB and 5,000 roles); the 25-page fixture does not establish production useful-result latency or throughput under real host pacing. The independent posting recall/precision corpus, representative phone and keyboard use, and the agreed operating envelope remain unqualified, so J2 remains at 77 pending that evidence.

Migration 0050 must precede the new worker. It backfills existing staged page times from their generation start and gives an old writer a sentinel default that the new reader interprets conservatively. After a new worker publishes a chunk, only the new worker implementation should resume that generation: an old worker does not honour the publication cursor. If rollback to old code is contemplated, pause continuation claims and use a separately tested rollback or roll-forward procedure; this local work does not establish one. No production deployment or live paid-AI scan is claimed here.
