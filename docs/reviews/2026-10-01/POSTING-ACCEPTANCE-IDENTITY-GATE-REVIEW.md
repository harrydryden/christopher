# Posting acceptance result-identity gate review

Observed 1 October 2026. This review concerns the local acceptance reporter, not a live posting-quality result. No live HTTP or paid model call was made.

## Defect and remedy

`summariseLiveAcceptance` previously counted result rows without requiring one result for each selected case. In a no-network reproduction, selected cases A and B with two identical, fully qualifying A results and no B result produced `sourceMatches=2`, `countLabelled=2`, `countMatches=2`, `postingIdentityLabelled=2`, `total=2`, and `liveAcceptanceVerdict=pass`. A qualified result with an unknown ID could also enter posting-identity aggregates, though that injection alone did not pass the two-case probe. The observed pre-fix output is retained in [before-fix-observation.json](implementation-evidence/acceptance-identity/before-fix-observation.json). The repo-relative [reproduction fixture](implementation-evidence/acceptance-identity/reproduce.ts) now checks that those invalid IDs throw; run it from the repository root with `pnpm exec tsx docs/reviews/2026-10-01/implementation-evidence/acceptance-identity/reproduce.ts`. Its current output is [current-gate-output.json](implementation-evidence/acceptance-identity/current-gate-output.json). The pre-fix observation and current gate output are separate evidence, not two results from the same code revision.

Scoring now rejects duplicate selected case IDs, unknown result IDs and duplicate result IDs before aggregation. A missing selected result remains a valid diagnostic input, but its unique result coverage blocks acceptance. Incomplete coverage no longer presents the selected-corpus discovery denominator as a measured threshold failure. The reporter separately counts observed labelled count disagreements, so a wrong manual count or a qualifying reference with unequal exact counts fails even if another case is missing; the absent case does not itself count as a disagreement. A directly observed wrong automatic source or posting-identity failure also fails with incomplete coverage. Full-corpus threshold behaviour and the existing human review, raw hash, 24-hour recency, complete-scope and required-corpus gates are unchanged.

## Evidence boundary

The 20 September frozen eight-source extraction oracle contains 3,423 machine-enumerated posting identities and is useful cross-parser evidence, not independently human-labelled posting recall or precision. The only two acceptance reference snapshots are Zapier (10 identities) and Datadog (436 identities); both sibling raw files match their recorded SHA-256 hashes, but both snapshots are `machine_enumerated`, `completeScope:false`, and older than the 24-hour qualification limit. Datadog's Greenhouse feed is not an attested equivalent of its labelled first-party all-jobs page. No current independently human-reviewed full-scope posting corpus was found. The acceptance reporter must continue to block a release verdict until fresh, source-bound human labels exist for the required cases.

The separate [live Siemens two-claim observation](implementation-evidence/partial-publication/live-siemens-claims.json) materially strengthens the narrow claim that partial publication can expose useful roles under real host pacing: one verified synthetic follower had 119 jobs and matching views after the first 50.3-second claim, then 239 after a second 53.3-second claim; the scan remained nonterminal and the continuation task queued. It does not establish terminal completeness, posting recall or precision, a representative source sample, a sustained operating budget, or unaided user success. Independent J2 recommendation remains **77/100** (completeness 4, robustness 3.5, UX/UI 4): live positive availability now has direct evidence, but the robustness floor of 4 and completeness floor of 4.5 require broader source and labelled-outcome evidence. This is a scope judgement, not an automatic refusal to recognise the live gain.
