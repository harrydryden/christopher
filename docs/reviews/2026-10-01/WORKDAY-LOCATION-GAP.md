# Workday multi-location admission gap — 1 October 2026

## Observed failure

The saved [Workday listing response](implementation-evidence/workday-region/workday-page.json) is a public, first-page response with 20 actual postings out of a reported 371. Seven postings use a count in `locationsText` (`2`, `3`, `4` or `70 Locations`) instead of place names. The posting `JR-0108691` says `70 Locations`. Its [public detail response](implementation-evidence/workday-region/workday-multi-location-detail.json) names `USA, GA, Atlanta` as the primary location and 69 additional locations, including `USA, MA, Boston` and `USA, WA, Seattle`. The [listing observation](implementation-evidence/workday-region/workday-observation.json) and [detail observation](implementation-evidence/workday-region/workday-detail-observation.json) record HTTP 200 and capture times of 20:21 and 20:23 UTC respectively. Recomputed SHA-256 digests of the saved bodies match those observations: listing `8d8f8e3ad2963bf5dc861edaa34b1c64729b0c701bdfad50882229c92004b326`; detail `2bd17c9cd795703fc79a21bc8ea30899b2bd31c922561196d2fa619a21a505c1`.

Today `mapPosting` in `packages/core/src/ats/workday.ts` stores `70 Locations` as the location. The scan's account gate then tests that literal text. A follower asking for **Boston** cannot match this posting even though the detail explicitly lists Boston; the posting is stored but has no admitted account view. An [offline reproduction](implementation-evidence/workday-region/boston-gate-reproduction.json) ran the actual Workday mapper on the saved posting inside an explicitly synthetic one-row pagination envelope: the Boston gate failed before detail enrichment and passed with the saved detail locations overlaid. That overlay demonstrates the gap; it is **not implemented** in the application. `fetch_description` does not repair this: `apps/worker/src/handlers/scan.ts` queues it for an admitted posting or a description-dependent gate, while this posting can fail the location gate before either condition applies. `apps/worker/src/handlers/description.ts` does re-run follower gates when it has text, but the Workday adapter has no detail JSON fetch in `fetchDescriptionFor`, and that handler does not extract `additionalLocations`. The listing alone also cannot prove UK eligibility for this particular posting: the observed 70 places are in the USA.

The first listing pages for [3M](implementation-evidence/workday-region/3m-page.json) and [Workday](implementation-evidence/workday-region/workday-page.json) contain postings in multiple countries. That supports two multi-region **board observations**, but a first page and one detail read do not establish complete listing coverage, extraction recall or acceptance of every location. The separate `remoteType` mapping issue is outside this design; `Flex` must not be treated as unrestricted remote work.

## Recommended implementation

1. Recognise a strict Workday count placeholder such as `70 Locations` in the adapter as **unknown location coverage**, preserving the raw label and count for display/provenance but not placing the count in the gate's `location` or `locations` fields. A named primary place in the posting path is not proof that the location list is exhaustive. Use an explicit resolution state, for example `pending | resolved | unavailable` plus the listing observation/version, rather than interpreting `null` as complete. A placeholder must neither pass every location filter nor become a definitive negative result.
2. At positive scan publication, identify a stored placeholder posting whose title/department/description passes at least one follower's non-location criteria but whose configured location filter needs real places. Queue durable, deduplicated Workday location enrichment in the **same transaction** as the posting. The task should name the job and the listing observation/version. A later follower or changed gate must also find and queue unresolved candidates during gate re-evaluation. A posting with no follower needing location detail can remain unresolved without a detail request.
3. Have a dedicated non-AI task fetch only that posting's tenant/site-scoped `/wday/cxs/{tenant}/{site}{externalPath}` JSON through the normal fetch context, host pacing, lease and retry machinery. Validate the URL against the source; parse `jobPostingInfo.location` and `additionalLocations` as bounded, non-empty strings, deduplicate them and retain the raw evidence/version. One task makes at most one detail request per attempt. Deduplication, a per-source request budget and a durable continuation/back-off bound work on a large board; reaching a budget leaves explicit pending work, never a silent final rejection. Re-fetch only when the listing's relevant version changes or the stored resolution expires, not on every daily scan.
4. In a fenced transaction, refuse an obsolete response if the job/source or listing observation has advanced. Store the resolved locations without allowing the next listing's `N Locations` placeholder, including one replayed from a listing snapshot, to overwrite them. Re-evaluate **all current followers** under the same gate-lock ordering used by `refreshFollowers`, insert/update/archive account views as appropriate and admit scores only for newly eligible, unscored views. Preserve existing decisions and score inputs unless an actual input changed. Share the follower gate-writing path with `fetch_description` rather than duplicating subtly different admission rules.
5. If detail is missing, malformed, host-busy or exhausted after retries, keep the catalogue role and its location state unresolved; surface the pending/failed admission in Health or scan diagnostics with a retry route. A listing's complete/partial status and two-miss closure logic continue to depend on listing coverage, **never** on a failed location-detail request. Account results must not imply that all location-gated roles were checked while unresolved candidates remain. `verifyRead` must remain its current one-page listing probe, with **zero** per-posting detail requests.

## Focused verification needed

- Adapter fixture: `70 Locations` is unknown, not a place or an automatic match; one detail response resolves Atlanta plus 69 additional places, including Boston and Seattle. A Boston gate fails before resolution and passes after it; a UK gate still fails for this captured posting. Remote/Flex behaviour has separate tests.
- Queue/integration fixture: the initial scan stores the role and durable enrichment request even though the Boston view is absent; a completed task creates that view and queues any needed score once. Duplicate claims, retries, new followers, changed gates and a newer listing observation remain idempotent and correctly fenced.
- Failure/coverage fixture: malformed detail or request-budget exhaustion leaves a visible unresolved state, no fabricated account match and no closure. A newer named-location listing cannot be overwritten by an older detail result. Source verification records exactly one listing-page request and no detail request.

This is an implementation design based on saved public responses, not a claim that location enrichment or a full multi-region corpus run has passed.
