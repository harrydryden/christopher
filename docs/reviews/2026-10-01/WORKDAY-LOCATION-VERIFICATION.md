# Workday location enrichment — local verification, 1 October 2026

**The observed `N Locations` defect has a targeted local implementation, but its release and broad outcome are not yet qualified.** This checkpoint updates the earlier [gap and proposed design](WORKDAY-LOCATION-GAP.md), whose statement that enrichment was unimplemented is historical. No production migration or deployment was performed.

## Observed defect and resulting behaviour

The saved [first Workday listing page](implementation-evidence/workday-region/workday-page.json) contains 20 of a reported 371 postings; seven show a count rather than named places. `JR-0108691` says `70 Locations`, while its independently saved [public detail JSON](implementation-evidence/workday-region/workday-multi-location-detail.json) identifies Atlanta and 69 additional US places, including Boston and Seattle. Previously the mapper stored the literal count as a job location, so a Boston follower missed a role whose detail explicitly names Boston. The listing and detail observations, capture times and hashes remain in the [original gap report](WORKDAY-LOCATION-GAP.md). This one posting is not evidence of UK eligibility or full-board recall.

The Workday adapter now marks a strict count placeholder `pending`, retains its label for provenance and excludes the count from gateable place names. A source-scoped detail reader makes one public JSON GET for the same tenant, site and job; it rejects redirects, malformed responses and a location list whose count does not agree with the placeholder. The saved 70-location response exercises that parser. A pending or unavailable location cannot satisfy a restricted location gate through an apparent place or an unrestricted Remote flag. Normal named locations and the separate explicit `remoteType: Remote` behaviour remain available.

Positive scan publication stores the unresolved role and a durable `fetch_locations` task together when at least one follower may need the locations. Synchronous subscription and settings re-evaluation can also queue a previously unresolved candidate, including a migrated row without a revision. The task is fenced by source, job and location revision; stale detail cannot replace a newer observation. Successful detail resolution writes the named locations and re-evaluates current eligible followers transactionally, including private-role visibility and archiving of newly ineligible views. Description refresh re-reads the current job after its fetch, so an older description result cannot reverse a concurrent location resolution.

On a later refresh with unknown locations, a previously qualified view is held only if its last verified named locations still pass the current gate. That prevents a temporary detail failure from falsely archiving a known match; it does not admit a new restricted view, preserve a view after a changed non-location gate, or treat legacy bare-count data as verified. Failed detail attempts leave the catalogue job unresolved and retryable without declaring the source listing incomplete or closing the role. Only a successful detail read updates `locationFetchedAt`.

The worker invalidates a stored AI fit score when the **primary** location, an existing score input, changes. Secondary named locations affect location admission but are not currently part of the score input. This is a consistency repair, not a claim about model output quality or whether the best display/scoring location was chosen. The detail request has a database-enforced budget of **50 attempts per hour per source**, shared across workers. When exhausted, a task is durably deferred to the next window before network access; failed HTTP reads count as attempts. This bound neither proves a 50-company daily run under 15 minutes nor establishes full Workday listing capacity.

The additive [0051 migration](../../../packages/db/drizzle/0051_workday_location_resolution.sql) and [0052 migration](../../../packages/db/drizzle/0052_workday_location_read_budget.sql) are required before this candidate worker runs: 0051 introduces resolution state and backfills old Workday count labels as pending; 0052 introduces the per-source request budget. This checkpoint is local only and does not assert mixed-version rollout or rollback safety.

## Verification and limits

The [core test log](implementation-evidence/workday-location-enrichment/core-tests.log) records **144/144** focused tests, including strict placeholder mapping, the saved 70-location detail shape, scoped URL/count rejection, gate semantics and task contracts. The [DB test log](implementation-evidence/workday-location-enrichment/db-tests.log) records **17/17** tests on an isolated local database, including synchronous gate enqueue, retained-view policy and budget boundary/concurrency/reset. [Core](implementation-evidence/workday-location-enrichment/core-typecheck.log) and [DB](implementation-evidence/workday-location-enrichment/db-typecheck.log) typechecks passed. The final [dedicated worker handler log](implementation-evidence/workday-location-enrichment/worker-location-tests.log) records **12/12** passes, including the last title-exclusion queue regression. The earlier [focused end-to-end log](implementation-evidence/workday-location-enrichment/worker-focused-e2e.log) records **22 passes and 86 deliberately skipped unrelated cases**; it predates that final refinement and must not be read as a post-refinement rerun. A separate [deferred-task wakeup check](implementation-evidence/workday-location-enrichment/worker-deferred-wakeup.log) records **1 pass and 5 skipped unrelated cases**. Final [worker typecheck](implementation-evidence/workday-location-enrichment/worker-typecheck.log) and [build](implementation-evidence/workday-location-enrichment/worker-build.log) passed. These tests use saved or synthetic responses and local databases, not a new live full-board run.

The [web evidence](implementation-evidence/workday-location-web/README.md) records a synthetic three-role Health and Companies fixture, keyboard retry, a stopped-worker state and a later scheduled retry. The earlier broad focused web regression passed **192/192** tests. After the scheduled-state change, **3/3** focused future/due/stopped query and component tests, web typecheck and production build passed. Browser checks at 1280px and 375px found no document overflow or page errors. The 375px enlargement doubled CSS text sizes. It was not native 200% browser zoom, an assistive-technology check or a user study. The fixture made no live Workday, AI, email or external listing calls.

J2 benefits from removing this observed hidden-city false negative and from a durable, bounded retry path. J8 benefits from explicit pending/failed/scheduled recovery states. J9 gains a local cross-worker budget and migration contract, without hosted operational proof. **Their canonical scores remain J2 77, J8 83 and J9 70.** The 90-point objective still requires independently human-labelled full-scope posting recall and precision, a real bot-protected corpus case and final-corpus runs, configured provider verification, live operating-capacity and release/restore evidence, and representative usability and accessibility sessions. No metric from this targeted implementation substitutes for those gates.
