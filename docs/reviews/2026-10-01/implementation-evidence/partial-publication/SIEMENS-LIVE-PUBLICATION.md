# Siemens: fresh live partial-publication check

Observed 1 October 2026, 17:14:10–17:15:55 UTC. A fresh isolated local PostgreSQL database (`ava_source_publication_live`) held one Siemens HTML source, one queued scan and one verified synthetic follower. The follower's deliberately empty keyword and location gate admits every parsed role; its matching views **do not establish personal relevance or posting precision**. The [first-party source audit](../../../2026-09-29/SOURCE-LABEL-AUDIT.md) traced Siemens' company jobs page through its Careers Marketplace to the [SearchJobs listing](https://jobs.siemens.com/en_US/externaljobs/SearchJobs/). This check used that public listing through the normal production worker fetcher, including its robots and host-pacing controls, with no host map, browser, model, email or production database. The process claimed only the scan task; it did not run the queued description or scoring workers.

The [harness](../../../../../apps/worker/src/live-html-publication-audit.ts) imposed a 180-second per-claim deadline, ten-minute overall budget, three-claim and 60-page caps. It stopped after two successful claims because the first had useful published positives. The fresh fixture and disabled AI/browser state are recorded in the [initialisation log](live-siemens-init.log); the [raw claim report](live-siemens-claims.json) records each public response URL, HTTP status and server `Date` header, and the [run log](live-siemens-run.log) records the claim outcomes. All 42 successful listing responses were HTTP 200, between 17:14:14 and 17:15:55 UTC. Claim 2 re-read two boundary pages before the next 20 pages. There was no redirect in those observed response URL pairs. The wrapper's `requestCount` counts successful `fetchText` listing responses; it cannot account for internal robots requests, retries or lower-level transport activity. Its `transferredBytes` field is the **decoded HTML body byte count** (3,268,924 then 3,577,216), not wire-transfer bytes.

The first useful catalogue and follower rows therefore appeared after about 50 seconds of this run, while the source remained explicitly incomplete. After claim 2, the generation still had a durable next URL at offset 240, `published_page_count=40`, `published_new_count=239`, zero restarts and an unchanged source fingerprint (`36ddf0affb6b878c47c7e99690b825b34fce9be5c377a08f52e7381b89017489`). The task was queued; the source stayed active with `last_ok_scan_at`, `last_postings_count`, `next_scan_at`, content hash and recipe still null, and zero consecutive failures. There was no terminal scan marker. The generation's expiry remained 19:14:10 UTC. This is a truthful partial state, not evidence of full board coverage or a successful final scan.

The independent [read-only SQL](live-siemens-readback.sql) and [database result](live-siemens-readback.json) confirm **40 staged pages** holding 239 postings, 239 distinct source job URLs and external keys, 239 seeded open jobs, 239 seeded in-table follower views, and exactly 239 `discovered` events. No duplicate job identities, closed jobs, positive missing counters, first-missed timestamps or closed events appeared in this initially empty fixture. Those zero closure counts are expected for an empty starting catalogue; they do not test negative reconciliation against previously known roles. There were 239 queued `fetch_description` tasks and one queued scan task, with no scores or AI calls. Description quality, scoring and notification delivery were not exercised.

The raw claim JSON reports `stagedPages` as 119 and 239. That diagnostic field was wrong: its original SQL expanded each page's posting array before `count(*)`, so it counted postings. The pre-claim 60-page cap used a separate correct page query and was unaffected. After the run, the harness query was corrected to count distinct page indexes and the database was read without making another public request. A further post-run diagnostic correction saves failed-claim responses, elapsed time, error and available checkpoint state before task-failure bookkeeping; it was not exercised by this successful run. The code loaded by the live process had SHA-256 `cd4d0e864fa8c1a21f7d031578f22fdf8f583e8350c69bb2e89cc87a34848a73`; the current on-disk harness has SHA-256 `e6dceff1ee5c4e1aa6a8c06da43066e1387858e31c9ec6abdeae49810bad0bfd` and passed worker typecheck. The raw result was retained unchanged. The durable page count of 40 and the per-claim 20-page increments come from the cursor and corrected database readback.

On 29 September, the [earlier normally paced Siemens continuation](../../../2026-09-29/implementation-evidence/source-audit/SIEMENS-CONTINUATION-LIVE.md) recorded 20 staged pages and 120 roles after 50.8 seconds, with zero published jobs under the previous terminal-only implementation. Today's first claim published 119 observed roles after 50.3 seconds. These are separate live observations on different dates and listing content, not a controlled speed or recall comparison. This check establishes early useful publication for one large public listing under normal pacing and a second claim without duplicate creation. It does not qualify the full Siemens listing, posting identity precision, or the 50-company daily-run target.
