# A5 score publication lock audit

Reviewed against the concurrent implementation on 1 October 2026. The publication transaction takes the global A5 model fence, the account input fence, the account's gate row, the company row, the job row, then the account's view row before recomputing the score fingerprint and writing the score (`apps/worker/src/handlers/learning.ts`). A pre-lock read of `jobs.company_id` locates the company; the locked job read checks that the association has not changed.

| Score input or eligibility | Production writer and protection | Follow-up after a committed change |
| --- | --- | --- |
| Latest preference profile / seed profile | `packages/db/src/profiles.ts` takes the account fence before the profile version lock and insert. `apps/web/lib/settings.ts` takes it before writing `seedProfile`. | A changed profile queues `rescore_all` with the version insert for a verified member or administrator; a seed profile save uses the caller's verification policy. |
| Latest confirmed CV Library | `apps/web/lib/cv-library-write.ts` takes the account fence before the Library version lock and insert. `apps/web/app/actions/cv.ts` gap quiz takes the account fence at its outer transaction entry before draft locks. | Library save queues `rescore_all` in the same transaction for a verified member or administrator. |
| Decision digest / target role choice | `apps/web/lib/decisions.ts` takes the account fence before role view locks and decision mutation. The outer transactions in `apps/web/app/actions/applications.ts` and the Undo actions in `apps/web/app/actions/decisions.ts` take it before their earlier view locks. Direct tag editing and worker tag_reason also take it before decision updates. | Decision edits and tag edits queue `rescore_all` for a verified member or administrator; synthesis may later create a new profile version. |
| Account gate, location terms, keyword terms, in-table and archive state | Gate saves and suggestion acceptance take the account fence before settings and view locks. The publisher holds the gate row and its target view. Scan, description and location writes hold their existing gate/job/view row locks. | Gate saves queue re-evaluation and, when verification permits, rescore; scan and enrichment queue exact score requests on input changes. |
| System A5 model and stage route | `apps/web/lib/settings.ts` takes the global model fence before `defaultModel`, `modelOverrides` or `stageRoutes` writes. The score's fresh input now pins the resolved A5 model and effort, so the provider call and fingerprint use one route. | Model setting save queues `rescore_all` for existing verified members and administrators in the same transaction. |
| Company name and existence | Publication holds the company row before the job and view. Admin rename, applied name suggestion, discovery rename and company deletion update/delete that row. | All three rename paths enqueue `rescore_all` for affected followers who are verified members or administrators in the same transaction. |
| Job title, description, location, status and ownership | Publication holds the job row after the company row and before the view. Description/location/scan writers update the job before target views. Source retirement was reordered to update jobs before locking views. | Source, scan and enrichment paths already queue score work or mark a closed role. |
| Unfollow | `apps/web/app/actions/companies.ts` takes the account fence before deleting a subscription/view and updating the shared company status. | The deleted view cannot receive a score. |

The `scoreAttemptVersion` on `user_jobs` is a separate compare-and-swap guard against an older provider answer landing after a newer request, including requests prepared within the same millisecond. Old batch records without a request number cannot publish and are requeued when necessary.

`apps/worker/src/score-publication-concurrency.test.ts` uses two independent PostgreSQL connections and observes actual blockers with `pg_blocking_pids`. It tests profile and other-role decision changes before publication, publication before a profile writer, company deletion, unfollow's view-then-company mutation under the account fence, and same-clock attempt ordering. The unfollow and other-role decision cases reproduce the SQL protocol with explicit fences; they do not call authenticated web actions.

These are application-level fences for the audited production writers. Direct SQL changes and older running processes do not take them; migration 0053 therefore requires a coordinated rollout as documented in `docs/DEPLOY.md`.
